# E2E 시나리오

스테이징(`https://zigzaego.example.com`)의 화면을 브라우저로 따라가며 확인하는 시나리오 목록과, 이를 Playwright로 자동화한 테스트의 참고 사항을 적은 문서이다.

## 개요

- 시나리오는 사용자가 화면에서 하는 동작과 그 결과를 영역별 표(ID, 전제, 단계, 기대)로 정의한다.
- 자동화한 시나리오는 `frontend/e2e/`의 Playwright 테스트와 ID로 연결한다. 테스트 제목은 `[ACC-01] ...`처럼 이 문서의 ID로 시작한다.
- 테스트는 스테이징의 실제 프런트엔드와 API를 대상으로 실행하며, 가입, 로그인, 온보딩 진입, 화면 이동처럼 반복 실행해도 결과가 같은 경로를 확인한다.

## 테스트 대상

**환경**
- 프런트엔드: `E2E_BASE_URL`, 기본값은 `https://zigzaego.example.com`이다.
- API: `E2E_API_URL`, 기본값은 `https://zigzaego.example.com`이다.
- 운영 주소는 호출할 수 없다. `frontend/playwright.config.ts`는 `E2E_BASE_URL`의 호스트가 `zigzaego.example.com` 또는 `localhost`가 아니면 오류로 중단하고, `frontend/e2e/support.ts`는 `E2E_API_URL`의 호스트가 `zigzaego.example.com` 또는 `localhost`가 아니면 오류로 중단한다.

**브라우저와 뷰포트**

| 프로젝트 | 브라우저 | 뷰포트 | 표의 뷰포트 열 |
|---|---|---|---|
| `phone` | Chromium | 375 x 812 | `375` |
| `desktop` | Chromium | 1360 x 800 | `1360` |

표의 뷰포트가 `양쪽`인 시나리오는 두 프로젝트에서 모두 실행한다. `375` 전용 시나리오는 테스트 안에서 `onlyPhone()`으로, `1360` 전용 시나리오는 `onlyDesktop()`으로 나머지 프로젝트를 건너뛴다.

**자동화한 영역**

현재 자동화한 시나리오는 `frontend/e2e/`의 스모크이며 ACC-01, ACC-02, ACC-06, ACC-08, ACC-10, ONB-01, ONB-02, ONB-03, ONB-04, ONB-05, HOME-01, ORD-01, HIS-01, RCP-01, SUP-01, ING-01, MORE-01, COM-01, COM-03이다. 표에서 `자동 예정`인 항목은 다음 티켓에서 구현한다.

| 티켓 | 시나리오 |
|---|---|
| S15P31A308-293 | ACC, ONB(`자동 예정` 항목), COM-01, COM-03, COM-04, COM-05 |
| S15P31A308-294 | HOME, ORD |
| S15P31A308-295 | HIS, MORE |
| S15P31A308-296 | RCP, SUP, ING |

## 포함하지 않는 대상

1차 자동화는 표준적인 경로 중 반복 실행해도 결과가 같은 것만 대상으로 한다. 아래 항목은 1차에서 뺐고, 재검토한 뒤 자동화 여부를 정한다. 시나리오 목록에서 자동화 열이 `1차 제외`인 항목이 여기에 해당한다.

| 항목 | 시나리오 | 제외 이유 |
|---|---|---|
| 메뉴 분석 | ONB-06, ONB-07, MORE-05 | 외부 유료 호출(LLM). 재검토 예정 |
| 영수증 OCR 업로드 | `ONB-09`의 `올리기` 이후 흐름 | 외부 유료 호출. 재검토 예정 |
| 시세 비교 | ORD-07 | 시세 데이터가 수집 상태에 따라 달라진다 |
| 외부 앱 창, 웹 푸시 | ORD-06, MORE-07, COM-06, COM-07 | 브라우저 자동화로 열거나 받을 수 없다 |
| 오류, 취소 상태 | ONB-08, HOME-03, HIS-03, HIS-04 | 스테이징에서 그 상태를 일으킬 수단이 없다 |
| POS 파일 업로드 | MORE-06 | 실제 POS 내보내기 파일이 필요하다 |
| 재료 끌어 놓기 | ING-04 | 입력 방식이 기기마다 다르다 |

ONB-04와 ONB-05는 가게 검색의 외부 수집(Apify) 결과가 일정하지 않으므로 `GET /onboarding/places` 응답을 대체해 실행한다.

이 밖에 운영 환경(`E2E_BASE_URL`, `E2E_API_URL`이 운영 호스트인 경우)은 설정 단계에서 막혀 대상이 아니다.

## 실행 방법

`frontend` 디렉터리에서 실행한다.

1. 의존성을 설치한다: `npm ci`
2. Chromium을 설치한다: `PLAYWRIGHT_BROWSERS_PATH=0 npx playwright install chromium`
3. 테스트를 실행한다: `npm run e2e`

- 브라우저를 `PLAYWRIGHT_BROWSERS_PATH=0`으로 설치하면 `node_modules` 안에 놓이므로, 실행할 때도 같은 환경변수를 지정해야 한다.
- 한 파일이나 한 프로젝트만 실행하려면 `npx playwright test e2e/specs/onb.spec.ts`, `npx playwright test --project=phone`처럼 Playwright 옵션을 붙인다.
- `workers`는 1, 실패한 테스트의 재시도(`retries`)는 1이다.
- CI에서는 `e2e:staging` 잡이 `develop` push 중 `frontend/`, `backend/`, `.gitlab/ci/e2e.yml`이 바뀐 파이프라인에서 자동 실행되고(같은 파이프라인에 스테이징 배포 잡이 있으면 그 뒤), 그 외 `develop` 파이프라인에서는 수동(`when: manual`) 실행할 수 있다. 또한 `develop` 예약 실행(하루 1회 `schedule`)과 GitLab Run pipeline(`web`) 수동 실행에서는 빌드·배포 잡 없이 `e2e:staging`만 돈다. 실패해도 파이프라인을 막지 않는다. 잡은 아티팩트를 남기지 않는다. 리포트와 trace에 시험 계정 비밀번호가 남을 수 있기 때문이다.

**환경변수**

| 이름 | 기본값 | 용도 |
|---|---|---|
| `E2E_BASE_URL` | `https://zigzaego.example.com` | 화면 주소 |
| `E2E_API_URL` | `https://zigzaego.example.com` | 계정 가입과 로그인에 쓰는 API 주소 |

**결과 확인**
- `frontend/playwright-report/`: HTML 리포트. `npx playwright show-report`로 연다. 실행이 끝나도 브라우저를 자동으로 열지 않는다.
- `frontend/test-results/`: 실패한 테스트의 trace가 남는다(`trace: retain-on-failure`). `npx playwright show-trace <trace.zip>`으로 연다.
- 두 디렉터리와 `frontend/e2e/.auth/`는 `.gitignore` 대상이다.

## 테스트 계정

- 실행을 시작할 때 `setup` 프로젝트(`frontend/e2e/auth.setup.ts`)가 새 계정을 가입하고 `frontend/e2e/.auth/account.json`에 저장한다. `phone`과 `desktop`은 이 계정을 함께 쓴다.
- 이메일은 `e2e+<UTC 시각>-<난수>@zigzaego.example.com` 형식이고, 비밀번호는 실행마다 무작위로 만든다. 가입 시 필수 약관 셋에 모두 동의한다.
- 이 계정은 가입만 마친 미완료 계정이다. 앱 화면을 확인하는 테스트는 `completeAccount()`로 만든 완료 계정을 쓴다. 이 헬퍼는 가입한 뒤 API로 재료(`POST /ingredients`), 메뉴(`POST /menus`), 레시피(`POST /recipes`)를 차례로 만들고, 가게 설정의 온보딩과 레시피 확인이 끝난 계정을 돌려준다. 메뉴 분석(외부 LLM)을 부르지 않으므로 스테이징에서 바로 쓸 수 있다.
- 테스트 계정은 `e2e+` 접두로 식별한다. 테스트는 가입한 계정을 삭제하지 않는다. 정리 스크립트는 이 저장소에 없으며, 테스트 계정은 인프라 담당이 정리한다.

## 테스트 추가 방법

1. 이 문서의 해당 영역 표에 시나리오 행을 추가한다. ID는 영역 약어와 두 자리 번호이고, 자동화와 뷰포트 열도 채운다.
2. `frontend/e2e/specs/<영역>.spec.ts`에 테스트를 작성한다. 제목은 `[ID] 제목` 형식이다. 현재 파일은 `acc.spec.ts`, `onb.spec.ts`, `home.spec.ts`, `ord.spec.ts`, `his.spec.ts`, `rcp.spec.ts`, `sup.spec.ts`, `ing.spec.ts`, `more.spec.ts`, `com.spec.ts`이며, 파일은 `phone`과 `desktop` 프로젝트에서 모두 실행된다.
3. 필요한 fixture와 헬퍼를 `frontend/e2e/support.ts`에서 가져온다.
4. 로컬에서 실행해 두 뷰포트에서 모두 통과하는지 확인한다.

**`support.ts`의 export**

| 이름 | 용도 |
|---|---|
| `test`, `expect` | Playwright의 `test`에 fixture를 더한 것과 `expect` |
| `account` (fixture) | `setup`이 가입한 계정(`email`, `password`) |
| `signedIn` (fixture) | `account`로 API 로그인해 받은 refresh token을 페이지에 심는다. 로그인한 상태로 화면을 열 때 쓴다 |
| `onlyPhone()`, `onlyDesktop()` | 테스트 안에서 호출하면 각각 `phone`, `desktop` 이외의 프로젝트를 건너뛴다 |
| `newAccount()`, `signup()`, `loginApi()` | 테스트 안에서 계정을 직접 만들거나 로그인할 때 쓴다 |
| `completeAccount()` | 계정을 가입시키고 API로 재료, 메뉴, 레시피를 만들어 온보딩까지 끝낸 완료 계정을 돌려준다 |
| `signInAs()` | 지정한 계정으로 로그인한 상태로 페이지를 연다. 테스트마다 다른 가게를 볼 때 쓴다 |
| `addSupplier()` | 완료 계정에 거래처를 하나 만든다 |
| `API`, `ACCOUNT_FILE`, `Account` | API 주소, 계정 파일 경로, 계정 타입 |

**로그인한 상태로 시작하는 테스트**

`signedIn`을 인자로 받으면 페이지를 열기 전에 로그인이 끝난다.

```ts
test("[ONB-01] 미완료 계정은 홈에서 가게 찾기로 이동한다", async ({ page, signedIn }) => {
  void signedIn;
  await page.goto("/");
  await expect(page).toHaveURL(/\/onboarding\/find$/);
});
```

**외부 API 응답 대체**

외부 수집처럼 결과가 일정하지 않은 호출은 `page.route`로 응답을 대체한다. `onb.spec.ts`는 가게 검색 응답을 다음과 같이 대체한다.

```ts
const places = (data: unknown[]) => ({ success: true, data, error: null });

await page.route("**/onboarding/places?*", (r) => r.fulfill({ json: places([PLACE]) }));
```

## 주의사항

- refresh token은 한 번만 쓸 수 있다. 앱은 이를 `sessionStorage`의 `wiggly-refresh` 키에 두므로 `storageState`로 넘길 수 없다. `signedIn`은 테스트마다 새로 로그인해 받은 토큰을 `addInitScript`로 심고, 새로고침해도 앱이 갱신한 토큰을 덮어쓰지 않도록 비어 있을 때만 심는다. 한 테스트 안에서 같은 토큰으로 `/auth/refresh`를 두 번 호출하면 두 번째는 실패한다.
- 실패한 테스트의 trace와 리포트에는 입력한 값(비밀번호 포함)이 남을 수 있다. `playwright-report/`와 `test-results/`를 외부에 공유하지 않는다.
- 운영 주소를 호출하지 않는다. `E2E_BASE_URL`과 `E2E_API_URL`은 스테이징 또는 `localhost`로만 지정할 수 있다.
- 실행마다 스테이징에 `e2e+` 계정이 여러 개 생긴다.

## 시나리오 목록

### 읽는 법

| 열 | 뜻 |
|---|---|
| ID | 영역 약어와 두 자리 번호. 테스트 제목의 접두사와 같다 |
| 전제 | 시나리오를 시작하기 전에 갖춰야 하는 계정 상태와 데이터 |
| 단계 | 사용자가 하는 동작 |
| 기대 | 화면에 보여야 하는 결과 |
| 자동화 | `자동`은 Playwright 테스트가 있어 실행한다. `자동 예정`은 1차에 자동화하기로 했으나 아직 테스트가 없다(문서만 있다). `1차 제외`는 이유를 함께 적고, 재검토 뒤 자동화 여부를 정한다 |
| 뷰포트 | `375`는 폰(하단 탭 막대), `1360`은 데스크톱(상단 알약 탭). `양쪽`은 둘 다 실행한다 |

전제의 계정 상태는 다음 둘로 나눈다.

- 미완료 계정: 가입만 마친 계정. 가게의 체크리스트에서 `ONBOARDING` 단계가 끝나지 않았다.
- 완료 계정: 메뉴가 저장돼 온보딩 단계가 끝난 계정. 가입만으로는 되지 않고, API로 재료, 메뉴, 레시피를 만들어 `completeAccount()`로 준비한다.

미완료 계정은 앱 화면(`(app)` 라우트)에 들어가면 `/onboarding/find`로 이동한다(`AppGate`). 그래서 홈, 발주, 이력, 레시피, 거래처, 재료, 더보기 시나리오는 완료 계정을 전제로 한다.
