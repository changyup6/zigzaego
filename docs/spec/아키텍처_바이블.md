# 위글리 자동 발주 AI — 프로젝트 핸드오프 문서

> 목적: 다른 ChatGPT 세션, 팀원, 멘토가 이 문서 하나만 읽어도 현재까지의 기획 의도, 확정 사항, 아키텍처, 구현 계획, 미결정 사항을 이해하고 바로 다음 논의를 이어갈 수 있도록 정리한 문서  
> 기준일: 2026-10-05  
> 프로젝트 성격: SSAFY 프로젝트 + 실제 협업 매장 PoC + 추후 범용 SaaS 확장

---

## 1. 한 줄 소개

위글리의 POS 판매 데이터, 메뉴별 레시피, 발주·입고 이력을 이용해 미래 식재료 수요와 소진 시점을 예측하고, 적정 발주 시점과 수량을 추천한 뒤 점주 승인 후 실제 거래처 주문까지 자동화하는 AI 기반 식당 발주 시스템.

---

## 2. 프로젝트 목표

### 1차 목표

실제 협업 식당인 `위글리`에서 사용할 수 있는 자동 발주 시스템을 만든다.

단순히 시연용 화면을 만드는 것이 아니라 다음 사이클이 실제로 동작하는 것을 목표로 한다.

```text
POS 판매 데이터 수집
        ↓
미래 메뉴 판매량 예측
        ↓
재료별 예상 소비량 계산
        ↓
추정 재고 / 소진 시점 계산
        ↓
발주 필요 여부 및 발주량 계산
        ↓
점주에게 발주 제안
        ↓
점주 승인 / 수정 / 거절
        ↓
실제 거래처 주문 실행
        ↓
결과 및 피드백 저장
```

### 장기 목표

위글리 한 매장에 하드코딩된 시스템으로 끝내지 않고, 다른 식당도 자신의 POS·레시피·거래처 데이터를 연결해서 사용할 수 있는 `범용 자동 발주 SaaS`로 확장한다.

### 현재 선택한 방향

프로젝트 방향은 다음 중 D로 확정했다.

```text
A. SSAFY 데모 중심
B. 위글리 실제 도입 중심
C. 처음부터 범용 SaaS
D. 위글리 실사용을 우선하되, 다른 식당으로 확장 가능한 구조
```

현재 결정: `D`

## 3. 현재 확보 가능한 데이터

위글리에서 다음 데이터는 확보 가능하다고 가정한다.

- POS 메뉴 판매 데이터
- 과거 발주 내역
- 거래처 정보
- 메뉴별 레시피
- 메뉴당 재료 소요량(BOM)

현재 어려운 데이터:

- 실시간 실제 재고량
- 모든 재료에 대한 매일의 재고 실사값

따라서 프로젝트는 `실시간 재고 측정 시스템`이 아니라 `판매량과 입고 이력을 이용한 이론 재고 추정 + 미래 수요 예측`을 중심으로 설계한다.

---

## 4. 핵심 문제 정의

초기 아이디어는 다음과 같았다.

> AI가 현재 재고를 파악하고 부족한 재료를 자동으로 주문한다.

하지만 실제 재고값을 지속적으로 확보하기 어려우므로 문제 정의를 다음과 같이 수정했다.

> POS 판매 데이터를 기반으로 재료 소비량과 미래 수요를 예측하고, 입고 및 발주 이력을 결합해 재료별 소진 시점을 계산한 뒤 적절한 시점과 수량으로 발주를 추천·실행하는 시스템.

중요한 점:

- 정확한 현재 재고량 자체를 맞히는 것이 핵심 목표가 아니다.
- 발주 시점과 발주량을 충분히 정확하게 결정하는 것이 핵심이다.
- 재고 오차는 안전재고(Safety Stock)와 추후 보정 로직으로 흡수한다.

## 8. 데이터 엔지니어링 영역

이 프로젝트에는 데이터 엔지니어링 업무가 명확하게 존재한다.

### 주요 역할

- POS 데이터 자동 수집
- CSV / Excel / API 데이터 수집
- 원천 데이터 정제
- 단위 통일
- 메뉴 / 재료 / 거래처 상품 Master Data 관리
- 데이터 중복 / 누락 검증
- 시계열 학습 / 추론 데이터셋 생성
- 예측 결과 저장
- 발주 결과 저장
- 점주 수정 이력 저장
- 모델 성능 평가용 데이터셋 생성

### 특히 중요한 문제: Master Data

식당마다 상품 이름과 단위가 다를 수 있다.

예:

```text
매장 A: 양파
매장 B: 깐양파
거래처 A: 국내산 양파 10KG
```

실제로는 동일하거나 대체 가능한 재료일 수 있다.

따라서 다음 구조가 필요하다.

```text
Raw Product
    ↓
Product Mapping
    ↓
Canonical Ingredient
```

예:

```text
국산 양파 10KG
→ ingredient_id = ONION
→ package_quantity = 10
→ base_unit = kg
```

이 표준화가 다른 음식점으로 확장할 때 매우 중요하다.

## 9. LLM의 역할

LLM을 발주 판단의 핵심 모델로 사용하지 않는다.

### LLM 사용 후보

- 초기 Excel 구조 분석
- 메뉴 / 레시피 파일 파싱
- 비정형 상품명 정규화 후보 생성
- 거래처 상품 ↔ 내부 재료 매핑 보조
- 발주 이메일 / 문자 생성
- 발주 추천 이유 자연어 설명
- 비정형 거래처 주문 규칙 분석

### LLM을 사용하지 않는 것이 좋은 영역

- 실제 발주 필요 여부의 최종 계산
- 정확한 수량 계산
- 현재 재고 산술
- 리드타임 계산
- MOQ 계산
- 주문 단위 반올림
- 중복 발주 방지

위 영역은 규칙 기반 / 코드 기반으로 처리한다.

## 10. 수요 예측 설계

### 목표

직접 `현재 재고량`을 예측하는 것보다 `미래 메뉴 판매량` 또는 `미래 재료 소비량`을 예측한다.

권장 메인 구조:

```text
미래 메뉴 판매량 예측
        ↓
메뉴별 BOM 적용
        ↓
미래 재료 소비량 계산
```

이 구조를 선호하는 이유:

- 설명 가능성이 높다.
- 메뉴별 판매 예측을 점주에게 보여줄 수 있다.
- 레시피 구조를 그대로 활용할 수 있다.
- 새로운 재료가 추가돼도 BOM으로 연결 가능하다.

## 11. 모델 후보

모델을 처음부터 하나로 확정하지 않는다.

실제 위글리 데이터에서 비교 후 선택한다.

### Baseline

반드시 필요하다.

후보:

- 직전 값
- 최근 N일 평균
- 최근 N주 같은 요일 평균
- 이동평균

### LightGBM / XGBoost

Feature 후보:

```text
day_of_week
weekend
holiday
lag_1
lag_7
lag_14
rolling_mean_7
rolling_mean_28
rolling_std_7
temperature
rain
promotion
```

### TimesFM

현재 주요 후보.

Time-Series Foundation Model의 zero-shot 성능을 활용할 수 있어, 매장별 데이터가 아주 많지 않은 상황에서 특히 검토 가치가 있다.

#### 2026-10 기준 주의사항

- TimesFM 3.0은 multivariate forecasting 및 covariate 지원이 강화된 최신 후보.
- 현재 TimesFM 3.0 pretrained weights는 비상업·비프로덕션 사용 제한이 있으므로 실제 위글리 운영 단계에서는 라이선스를 반드시 다시 확인해야 한다.
- TimesFM 2.5 weights는 실제 PoC 후보로 같이 검토할 가치가 있다.
- SSAFY 실험 단계에서 3.0 성능 평가를 하는 것과 실제 운영에 적용하는 것은 분리해서 판단한다.

중요:

`TimesFM이 최신이므로 사용한다`가 아니라 다음 근거로 선택해야 한다.

```text
Baseline
vs
LightGBM
vs
TimesFM

→ 실제 위글리 POS 데이터에서 비교
→ 가장 좋은 모델 채택
```

## 12. 예측 평가 방법

단순 MAE 하나만 보지 않는다.

후보 지표:

- MAE
- RMSE
- WAPE
- MAPE 또는 sMAPE
- Bias
- 품절 발생률
- 과잉재고율
- 폐기 추정량
- 발주 횟수
- 실제 점주 수정률

특히 프로젝트 최종 목표는 `판매량 예측 대회`가 아니라 `발주 효율화`이므로 비즈니스 지표도 같이 평가한다.

## 13. 재고 추정

실시간 재고값이 없으므로 다음 방식으로 추정한다.

```text
Estimated Inventory(t)
=
기준 시점 재고
+ 누적 입고
- 누적 이론 소비량
```

이론 소비량:

```text
메뉴 판매량 × 메뉴당 재료 소요량
```

예:

```text
라떼 100잔 × 우유 200ml
= 우유 이론 소비량 20L
```

## 14. 실제 재고와 추정 재고의 오차

오차 원인:

- 폐기
- 직원 식사
- 서비스 제공
- 조리 중 손실
- 레시피 편차
- 흘림
- POS에 기록되지 않은 소비
- 입고량 오류
- BOM 오류

실재고 정답이 자주 없다면 `재고량 ML`을 억지로 만들지 않는다.

대신:

```text
수요예측
+
Safety Stock
+
보수적인 발주 정책
```

으로 문제를 푼다.

## 15. 과거 발주 이력 활용

실제 재고가 없어도 과거 발주 주기와 발주량은 소비 패턴을 간접적으로 보여준다.

예:

```text
우유 30L 입고
→ 평균 4일 뒤 다시 30L 발주
```

BOM 계산상 30L가 5일간 사용돼야 한다면 실제 소비는 이론치보다 높을 가능성이 있다.

추후 보정계수 후보:

```text
Adjusted Consumption
=
POS 기반 이론 소비량
× ingredient_correction_factor
```

초기 MVP부터 복잡하게 만들 필요는 없다.

## 16. 발주 엔진

발주 엔진은 AI와 분리한다.

```text
AI
→ 향후 수요를 예측

Order Engine
→ 언제 / 무엇을 / 얼마나 주문할지 결정
```

## 17. 발주점 계산

기본 개념:

```text
Reorder Point
=
Lead Time Demand
+
Safety Stock
```

예:

```text
배송 리드타임 = 2일
내일 예상 소비 = 6L
모레 예상 소비 = 7L

Lead Time Demand = 13L
Safety Stock = 4L

Reorder Point = 17L
```

현재 Inventory Position이 발주점 이하라면 발주 후보가 된다.

## 18. Inventory Position

단순 현재 재고만 보면 안 된다.

이미 주문했지만 아직 도착하지 않은 상품을 반영해야 한다.

```text
Inventory Position
=
Estimated On-hand Inventory
+
On-order Inventory
-
Reserved / Committed Quantity
```

이를 반영하지 않으면 같은 상품을 매일 중복 발주할 수 있다.

---

## 19. 발주량 계산

개념:

```text
Required Quantity
=
Target Inventory
-
Inventory Position
```

이후 거래처 규칙 반영:

```text
Order Quantity
=
MOQ 적용
→ Pack Size 단위 올림
→ 유통기한 / 예상 소비량 상한 적용
```

예:

```text
필요량 18L
주문 단위 10L
→ 20L 주문
```

MOQ가 30L라면:

```text
→ 30L 주문
```

## 24. 결제 전략

초기 범위에서 `결제 자동화는 제외`한다.

우리 서비스의 1차 책임:

```text
수요예측
→ 발주 추천
→ 점주 승인
→ 주문 실행
```

결제:

```text
기존 거래처 결제 방식 유지
```

이유:

- 우리 시스템이 점주의 은행계좌에서 임의로 계좌이체하기 어렵다.
- 금융 API는 계약 / 인증 / 규제 이슈가 크다.
- PG 자동결제는 일반 거래처 송금과 다른 문제다.
- 발주 자동화만으로도 충분한 업무 절감 효과가 있다.

따라서 SSAFY / 위글리 PoC에서는 결제 자동화를 핵심 범위에서 제외한다.

## 37. 성공 기준

### 기술적인 성공

- POS 데이터가 매일 정상 수집된다.
- 메뉴 판매량에서 재료 소비량이 계산된다.
- N일 미래 수요를 예측한다.
- 발주 추천이 자동 생성된다.
- 실제 주문 채널로 연결된다.
- 결과가 로그에 저장된다.

### 운영적인 성공

- 점주가 추천 내용을 이해할 수 있다.
- 발주 수작업 시간이 줄어든다.
- 점주가 추천량을 지나치게 많이 수정하지 않는다.
- 품절 / 과잉발주 위험을 줄인다.

### 프로젝트 발표 관점

> 단순 AI 예측 모델이 아니라 `예측 → 의사결정 → 실제 업무 실행`까지 연결했다는 점을 강조한다.

## 46. 가격 연동 발주 (2026-10-06 추가)

### 목표

식재료 값이 오르내릴 때 같은 양을 같은 주기로 사지 않는다.

```text
값이 비쌀 때 → 적게 사고 자주 주문한다 (며칠치만, 값이 내릴 때까지 버틴다)
값이 쌀 때   → 많이 사고 드물게 주문한다 (상하기 전에 쓸 수 있는 만큼 미리 산다)
```

### 가격 데이터의 원천

1. 입고 확인 때 적는 단가 (거래명세서). 가장 믿을 수 있는 값. MVP는 이것만 쓴다.
2. 거래처 상품 단가를 설정 화면에서 고칠 때 자동 기록.
3. 외부 시세 (aT KAMIS 농산물 도매가, 축산물품질평가원 등). 4주차 이후. 거래처 단가가 없는 재료의 보조 지표.

### 가격 지수

```text
기준 단가 = 최근 8주 단가 이력의 중앙값
가격 지수 = 현재 단가 ÷ 기준 단가

비쌈  : 지수 ≥ 1 + θ   (θ 기본 0.10)
쌈    : 지수 ≤ 1 − θ
보통  : 그 외
이력 3건 미만 → 지수 1 (조정 없음)
```

중앙값을 쓰는 이유: 한 번 잘못 적은 단가에 휘둘리지 않기 위해서다.

### 발주 엔진에 넣는 방법

발주점(리드타임 수요 + 안전재고)은 건드리지 않는다. 바꾸는 것은 "며칠치를 사느냐"인 발주 주기 R뿐이다.

```text
R' = max(1, R × 0.5)   비쌈
R' = R × 2.0           쌈. 단 (shelf_life − lead_time)일치와 max_order_qty 이하
R' = R                 보통

목표 재고 = 안전재고 + Σ 예측 소비량(내일 … L + R'일 뒤)
```

R이 줄면 목표 재고가 줄어 추천량이 내려가고, 재고가 발주점에 더 빨리 닿아 다음 추천이 더 일찍 뜬다. 즉 "적게·자주"가 식 하나에서 같이 나온다. R이 늘면 반대다.

### 지키는 것

- 안전재고 아래로는 어떤 경우에도 내려가지 않는다. 품절을 가격으로 사지 않는다.
- 쌀 때 미리 사는 양은 유통기한과 품목별 최대 발주량을 넘지 않는다. 신선 재료는 기본적으로 가격 연동을 끈다.
- 추천 이유에 가격 한 줄을 항상 보여준다. 점주가 "왜 평소보다 적게 추천했지"를 바로 알아야 한다.
- recommendation 행에 price_ratio, price_level, cycle_days_used를 남겨 나중에 가격 효과(기준 단가 대비 절감액)를 집계한다.

### 나중에

- θ와 배수(0.5 / 2.0)를 재료별로 자동 조정. 수정률과 절감액으로 평가.
- 거래처 간 단가 비교와 대체 거래처 제안.
- 가격 급등 알림.

## 47. 멀티 테넌트 · 셀프 서브 설계 (2026-10-06 추가)

### 목표

다른 가게 사장님이 사이트에 들어와 가입하고 자기 가게를 만든 뒤, 위글리와 같은 화면으로 자기 가게 발주 자동화를 쓴다. 3주 안에 가입 화면까지 만들지는 않지만, 구조는 첫날부터 이렇게 짠다.

### 원칙

1. **가게(store)가 테넌트다.** 모든 테이블에 store_id. 계정과 가게는 N:N (store_member, 역할 OWNER/STAFF).
2. **store_id는 클라이언트가 보내지 않는다.** 로그인한 계정의 가게를 요청 컨텍스트에 넣고 미들웨어 한 곳에서 모든 쿼리에 강제한다. URL에 다른 가게 id를 넣었을 때 보이면 버그. 통합 테스트에 가게 2개를 둔다.
3. **위글리 고유값을 코드에 두지 않는다.** 가게 이름, 워드마크 문구, 메시지 템플릿, 마감 시각, 배송 요일, 포스 엑셀 형식, 안전재고 N, 가격 θ는 전부 store·supplier·ingredient 행의 설정값이다.
4. **포스 파서는 벤더별 어댑터.** 인터페이스는 "파일 → pos_sale 행"으로 고정하고, 벤더가 늘면 어댑터만 추가한다.
5. **추천 배치는 가게 단위로 돈다.** 가게 수가 늘어도 같은 코드.

### 온보딩 (셀프 서브의 뼈대)

가게를 만들면 설정 완료 체크리스트가 홈 상단에 뜬다. 5단계를 다 채우면 사라지고 첫 추천이 뜬다.

```text
1. POS 엑셀 업로드
2. 포스 메뉴명 연결
3. 레시피 입력 (주력 메뉴부터)
4. 거래처와 거래처 상품 입력
5. 핵심 재료 재고 실사 1회
```

3주 안에는 팀이 위글리 계정과 가게를 만들어 주고 체크리스트는 진행 상태 표시로만 쓴다. 4주차 이후 공개 가입과 위자드 화면을 붙인다.

### 3주 안에 하는 것 / 4주차 이후

| 3주 안 | 4주차 이후 |
|---|---|
| account, store, store_member 테이블 | 공개 가입 페이지, 이메일 인증 |
| 로그인, store 스코프 미들웨어 | 온보딩 위자드 화면 |
| 가게별 설정값으로 모든 하드코딩 제거 | 포스 벤더 추가, POS 자동 연동 |
| 설정 완료 체크리스트 API와 홈 표시 | 요금제, 한 계정이 여러 매장 보기 |
| 포스 파서 어댑터 인터페이스 | 가게별 모델 파라미터 |
