# 판매 데이터 사전 (Data Dictionary)

> 포스 엑셀 · 배달앱 판매 내역이 **어떤 열로 들어와서, 어떤 모양으로 `pos_sale`에 쌓이는지** 정의한다.
> 업로드 파서(S15P31A308-38)와 예측 노트북(`ai/`)이 같은 정의를 본다.

**상태: 샘플 형식 기준 초안.** 위글리 실데이터를 받기 전이다(S15P31A308-13 미팅). 실데이터가 오면 3절 · 6절을 채우고 "미확인"을 지운다.
벤더별 원본 형식 조사는 [POS · 배달앱 export 형식 조사](POS_export_형식_조사.md).

---

## 1. 데이터가 흘러가는 길

```
원본 파일 (가게마다 형식이 다름)          표준 판매 행 (모든 가게 같음)         DB
 포스 관리자 사이트 엑셀  ─┐
                           ├─ 벤더 어댑터 ─→  sold_date · menu_name · qty · channel ─→ pos_sale
 배달앱 사장님 사이트 엑셀 ─┘    (파일 → 행)                                              (+ menu 매핑)
```

- 원본 열 이름 · 순서 · 합계 행은 벤더마다 다르다. **어댑터가 원본을 2절의 표준 행으로 바꾸는 것까지** 책임진다
- 표준 행 아래로는 가게 · 벤더를 몰라도 된다. 예측 · 소비량 계산은 표준 행만 본다
- 원본 파일은 커밋하지 않는다. `ai/data/raw/`에만 두고 그 폴더는 `.gitignore`다 (팀 Secret 규칙)

## 2. 표준 판매 행 — 어댑터의 출력

하루 · 메뉴 · 채널마다 한 행.

| 열 | 타입 | 필수 | 예시 | 설명 |
|---|---|---|---|---|
| `sold_date` | date (`YYYY-MM-DD`) | ✅ | `2026-10-09` | 영업일. 가게 시간대(`store.timezone`) 기준 |
| `menu_name` | string | ✅ | `등심돈까스` | **원본 이름 그대로.** 공백 · 옵션 표기도 바꾸지 않는다. `pos_sale.raw_menu_name`에 저장 |
| `qty` | int ≥ 0 | ✅ | `53` | 판매 수량(그릇 · 개). 환불 · 취소를 뺀 순수량 |
| `channel` | enum | ✅ | `HALL` | `HALL` · `DELIVERY` · `NONE`. 4절 |
| `sold_at` | datetime | | `2026-10-09T12:31:00` | 원본이 건별(영수증 단위)일 때만. 일 단위 원본이면 비운다 |
| `amount` | int (원) | | `12000` | 매출액. 예측에는 안 쓰고 검증용으로만 |
| `source_file` | string | ✅ | `okpos_2026-04_10.xlsx` | 어느 업로드에서 왔는지. 재업로드 덮어쓰기 기준 |

규칙:

- **같은 (`sold_date`, `menu_name`, `channel`)은 한 행.** 원본이 건별이면 어댑터가 합친다
- **재업로드는 덮어쓴다.** 같은 가게의 같은 날짜 범위 · 메뉴가 다시 오면 기존 행을 지우고 새 행을 넣는다 (S15P31A308-38 완료 조건)
- 합계 · 소계 · 빈 행 · "할인" · "봉사료" 같은 비메뉴 행은 어댑터에서 버린다
- 옵션(곱빼기, 사리 추가)은 3주 안에는 **본 메뉴 수량에 합치지 않는다.** 옵션 행은 별도 `menu_name`으로 남기고, 레시피를 붙일지 말지는 메뉴 매핑 화면에서 정한다

## 3. 원본 형식 — 샘플 (현재 `ai/data/sample/`)

실데이터 전 테스트용. `uv run python scripts/make_sample_data.py`로 만든다. 모든 이름 · 수치는 가상이다.

아래 표 · 수치는 기본값(돈까스집 한 곳 · 730일)이다. 업종 · 규모가 다른 가게도 만들 수 있다 (S15P31A308-240):

- 가게 틀 7종 `--template`: `donkatsu`(돈까스, 기본) · `bunsik`(분식) · `chinese`(중식) · `korean`(한식 백반) · `chicken`(치킨) · `cafe`(카페) · `pasta`(파스타). 쉼표 목록 또는 `all`. `--list-templates` 로 목록
- `--stores N`: 가게 N곳. 돈까스 한 곳이 아니면 `가게키/`(예 `chicken-05/`) 폴더마다 아래 CSV 전부, 맨 위 `stores.csv`(`store_key` · `template` · `store_name` · `scale` · `seed`). `scale`(0.6 ~ 1.8)은 모든 메뉴 평일 평균에 곱한 규모 배수이고 `menus.csv` 의 `base_qty` 에도 곱해져 나간다
- `--days` 는 2021-01-01 ~ 2026-12-31 안에서 1 ~ 5년. 공휴일 · 설 · 추석 휴무 · 가상 지역 행사가 그 범위 전체에 있다
- `make_seed_sql.py` 는 `stores.csv` 가 있으면 가게마다 가게 · 데모 계정(`demo+가게키@wiggly.local`)을 만들어 한 파일에 넣는다. `--append` 는 빈 DB 대신 "넣으려는 가게 이름 · 계정 이메일이 이미 있으면 실패" 만 검사한다

## 4. 채널 구분 — 배달 · 홀

배달과 홀은 요일 패턴이 다르다(배달은 비 오는 날 · 주말 저녁에 몰린다). 그래서 예측은 **채널별로 따로** 하고 합친다. 원본이 어떻게 주느냐에 따라 세 경우가 있다.

| 경우 | 원본의 모습 | 어댑터가 하는 일 | `channel` |
|---|---|---|---|
| A. 포스에 채널 열이 있다 | "주문유형" · "판매구분" 같은 열에 홀 / 포장 / 배달 | 값을 매핑. 포장은 `HALL`에 합친다(가게 안에서 조리 · 수령) | `HALL` · `DELIVERY` |
| B. 포스와 배달앱이 따로다 | 포스 엑셀 = 홀만, 배달앱 사이트 엑셀 = 배달만 | 파일 종류로 결정. 두 파일을 각각 올린다 | `HALL` · `DELIVERY` |
| C. 구분할 수 없다 | 포스 한 파일에 전부 섞여 있고 구분 열이 없다 | 그대로 한 계열 | `NONE` |

- 포장(테이크아웃)을 따로 둘지는 실데이터에서 포장 비중을 본 뒤 정한다. 지금은 `HALL`에 합친다
- 배달앱 주문이 포스에 **연동되어 들어오는데 구분 열이 없으면** C다. 이때 배달앱 사이트 엑셀까지 따로 올리면 이중 집계가 된다 → 업로드 화면에서 막아야 한다
- 위글리가 어느 경우인지: **미확인** (S15P31A308-13에서 확인)

## 5. 0 · 결측 · 휴무 — 행이 없는 날을 어떻게 읽나

원본에는 "안 팔린 메뉴"와 "문 닫은 날"이 둘 다 **행이 없는 것**으로 나타난다. 둘을 구분하지 않으면 예측이 부풀려진다(안 팔린 날을 빼고 평균을 내니까).

| 상황 | 판단 | 표준 처리 |
|---|---|---|
| 그날 **가게 전체** 판매가 0 | 휴무 | 행을 만들지 않는다. 휴무일 목록에 넣는다 |
| 영업일인데 특정 메뉴 행이 없다 | 그 메뉴 0개 판매 | `qty = 0` 행으로 채운다 |
| 업로드한 파일 기간 밖 | 데이터 없음 | 아무것도 만들지 않는다. 0도 휴무도 아니다 |
| 앞으로의 휴무 | 가게 설정의 정기 휴무 요일 | 예측 대상 날짜에서 뺀다 |
| 원본 `qty`가 음수(환불이 수량보다 큼) | 원본 오류 | 0으로 자르고 업로드 결과에 경고 |
| 메뉴가 판매 기간 중간에 생겼다(신메뉴) | 첫 판매일 이전은 데이터 없음 | 첫 판매일 이전을 0으로 채우지 않는다 |

- 채널이 있으면 휴무 판단은 **채널별로** 한다. 홀은 쉬고 배달만 연 날이 있을 수 있다
- `ai/src/weglee_ai/baseline.py`의 `fill_daily`가 이 표의 1 · 2 · 6번째 줄을 구현한다. 백엔드 요일 평균도 같은 규칙이어야 결과가 같다
- 이 표는 팀 합의 전 제안이다. 확정되면 DECISIONS.md에 올린다
