## 1. 이번 세션에서 확정한 것

| 항목 | 결정 | 이유 |
|---|---|---|
| 자동화 레벨 | **Level 1** 기본. 추천 → 승인·수정 → 거래처별 주문 메시지 생성 → 사장님이 카톡 전송 → 입고 확인 | 카톡·전화 주문 거래처는 자동 전송이 불가능. 3주 안에 확실히 되는 범위 |
| Level 2 조건부 | 미팅에서 이메일 또는 웹 주문을 받는 거래처가 나오면 **그 한 곳만** 3주차에 자동 전송 추가 | 거래처 데이터 없이는 결정 불가 |
| 데이터 수집 | POS 관리자 사이트에서 뽑은 엑셀을 앱에 업로드 | POS 벤더 미확인. API 연동은 4주차 이후 |
| 예측 모델 | 최근 4주 같은 요일 평균. 휴무일 제외 | 3주 안에 ML을 서비스에 넣지 않는다. ML은 노트북에서 병렬 비교 |
| 서버 | Spring Boot 백엔드 1개. Python은 분석·실험용 | 요일 평균은 SQL 한 줄. FastAPI는 모델이 생길 때 추가 |
| 재료 범위 | 핵심 재료 10~15개 | 주력 메뉴 소수 식당. 전체 재료 BOM은 하지 않는다 |
| 재고 기준점 | 도입 당일 핵심 재료 실사 1회 | 추정 재고의 시작값 |
| 입고 기록 | 승인 시 입고 예정 생성, 사장님이 "입고 확인" 탭. 기본값은 주문 수량 | 이게 없으면 추정 재고가 돌아가지 않는다 |
| 재고 음수 | 0으로 보정하고 "실사 필요" 플래그 | 오차는 안전재고와 사장님 승인으로 흡수 |
| 안전재고 | 최근 7일 평균 소비량 × N일. N은 재료별 설정, 기본 1 | 통계식은 4주차 이후 |
| 확장 구조 | 첫날부터 멀티 테넌트. 계정·가게 테이블, 모든 조회에 store 스코프 강제, 위글리 고유값(이름·문구·마감) 하드코딩 금지. 공개 가입·온보딩 위자드는 4주차 | 다른 가게 사장님도 들어와서 자기 가게를 만들 수 있어야 한다. 나중에 넣으면 전부 뜯는다 |
| 가격 연동 발주 | 입고 단가를 기록해 가격 지수를 만들고, 비쌀 때는 적게·자주, 쌀 때는 많이·드물게 사도록 발주 주기 R만 조정 (4.8절) | 값이 오르내릴 때 같은 양을 사면 손해. 안전재고 아래로는 절대 안 내려가고 상하기 전에 못 쓰는 양은 안 산다 |
| 제외 | 결제, 날씨 변수, 보정계수, 폐기 추정, 웹 RPA, TimesFM 서비스 탑재, 다점포 UI | 전부 4주차 이후 백로그 |

## 2. 범위

### 들어가는 것

- POS 엑셀 업로드와 메뉴명 매핑
- 메뉴 · 재료 · 레시피 · 거래처 · 거래처 상품 관리 화면
- 재료별 일 소비량 계산
- 추정 재고 계산과 조회
- 메뉴별 7일 판매량 예측 (요일 평균)
- 발주 추천 생성 (매일 새벽 배치 + 수동 실행)
- 추천 승인 · 수량 수정 · 거절, 사유 기록
- 거래처별 주문 메시지 생성과 복사
- 입고 확인
- 발주 이력, 예측 vs 실제 저장
- 안전장치: 중복 추천 방지, 품목별 최대 발주량, 승인자 기록
- 계정·가게: 로그인, 가게 1개 생성, 모든 데이터와 API가 store 단위 (화면에 보이는 건 위글리 1곳. 계정은 팀이 만들어 준다)
- 가게 설정 완료 체크리스트: POS 업로드 → 메뉴 연결 → 레시피 → 거래처 → 재고 실사. 다 채우면 홈에서 사라진다
- 가격 이력: 입고 확인 때 단가 입력(기본값은 거래처 상품 단가), 거래처 상품 단가를 고치면 자동 기록
- 가격 연동 발주: 가격 지수에 따라 발주 주기·수량 조정, 이유 문장과 재료 상세에 표시

### 빠지는 것

- 거래처 자동 전송 (조건부 1곳 제외)
- POS 자동 연동
- ML 모델 서비스 탑재
- 결제
- 알림 발송 (4주차. 우선은 사장님이 아침에 앱을 연다)
- 한 사장님이 여러 매장을 보는 화면. 단, 계정:가게는 처음부터 N:N 테이블
- 외부 시세 API (농산물·축산물 도매가). 3주 안에는 입고 단가만 쓴다
- 가격 파라미터(θ, 배수) 자동 튜닝. 3주 안에는 기본값 고정

## 3. 주차별 계획

### 1주차 — 데이터 확보 + 뼈대

**완료 기준:** 샘플 또는 실제 POS 파일을 업로드하면 재료별 일 소비량 테이블이 나온다.

| 역할 | 할 일 |
|---|---|
| PM/Infra | 사장님 미팅 (질문지: docs/meetings/사장님_미팅_질문지.md). 레포, CI, Docker Compose(Postgres), 스테이징 서버 |
| Data/AI | 받은 POS 엑셀 프로파일링 → Data Dictionary. 실데이터 오기 전까지 쓸 샘플 데이터 생성 스크립트. 레시피 템플릿 → recipe CSV 변환 |
| BE 2 | DB 스키마와 마이그레이션 (계정·가게·store_member 포함). 로그인과 store 스코프 미들웨어 (모든 쿼리에 로그인한 가게의 store_id 강제). 엑셀 업로드 파서 + 메뉴명 매핑 (미매핑 메뉴는 사용자가 확인). 메뉴·재료·레시피·거래처 CRUD. 이론 소비량 쿼리 |
| FE 2 | 프로젝트 셋업. 업로드 화면 (매핑 확인 포함). 레시피 관리 화면. 거래처·재료 설정 화면 |

실데이터가 늦어도 멈추지 않는다. 샘플 데이터로 뼈대를 완성하고, 실데이터가 오면 교체한다.

### 2주차 — 엔진

**완료 기준:** 실데이터로 "오늘 발주 필요 품목"이 뜨고, 품목마다 근거 숫자가 보인다.

| 역할 | 할 일 |
|---|---|
| Data/AI | 요일 평균 베이스라인을 rolling 방식으로 검증 (WAPE, Bias). 재료별 안전재고 N 기본값 제안. 가격 지수 정의(최근 8주 중앙값 대비)와 θ·배수 기본값, 재료별 price_sensitive 기본값(신선 OFF, 냉동·상온 ON) 제안. LightGBM 노트북 시작 |
| BE 2 | 추정 재고 계산. 예측 함수. 발주 엔진 (발주점, 발주량, MOQ, 포장 단위 올림). 추천 생성 배치. 추천 조회 API. price_history 테이블과 기록 경로(입고 단가, 거래처 상품 단가 변경), 가격 지수 조회 |
| FE 2 | 홈 대시보드 (오늘 발주 필요, 곧 소진, 추정 재고). 추천 상세 (근거 숫자와 이유 문장) |
| PM/Infra | 사장님 레시피 작성 세션 진행. 스테이징에 실데이터 올리기 |

### 3주차 — 승인 + 전달 + 배포

**완료 기준:** 사장님이 폰으로 승인 → 메시지 복사 → 카톡 전송 → 입고 확인까지 실제로 한 사이클 돈다.

| 역할 | 할 일 |
|---|---|
| BE 2 | 승인·수정·거절 API. 승인 건을 거래처별 발주서로 묶기. 메시지 템플릿 렌더링. 입고 확인(단가 포함). 발주 엔진 가격 조정(4.8절)과 이유 문장 한 줄. 가게 설정 완료 체크리스트 API. 실행 로그. 안전장치. **(조건부)** 이메일 거래처 1곳 자동 발송 |
| FE 2 | 승인 플로우 (모바일 우선). 메시지 복사·공유 버튼. 입고 확인 화면(단가 입력칸). 재료 상세 가격 배지와 단가 추이. 로그인 화면과 설정 완료 체크리스트. 발주 이력 |
| Data/AI | 예측 vs 실제 저장 파이프라인. 평가 쿼리와 간단한 성능 화면. LightGBM vs 베이스라인 비교 결과 정리 (발표 근거, 4주차 교체 판단용) |
| PM/Infra | 운영 배포. 위글리 도입일 재고 실사. 사장님 사용법 교육 15분 |

### 4주차 이후 — 실사용 백로그

우선순위 순.

1. 사장님 수정률 모니터링. 특정 재료가 계속 수정되면 BOM 또는 안전재고 N 조정
2. LightGBM이 베이스라인보다 WAPE가 좋으면 교체. 이때 FastAPI 추가
3. 알림 (푸시 또는 카카오 알림톡)
4. Level 2 거래처 확대
5. 보정계수 (과거 발주 주기 대비 이론 소비량 차이)
6. POS 자동 수집
7. 다점포
8. 공개 가입과 온보딩 위자드. 다른 가게 사장님이 혼자서 가게를 만들고 첫 추천까지 가는 흐름
9. 외부 시세 API(농산물·축산물 도매가) 연결, 가격 파라미터(θ, 배수) 자동 튜닝, 가격 효과(기준 단가 대비 절감액) 집계
10. 포스 벤더별 엑셀 파서 추가 (파서는 1주차부터 벤더별 어댑터로 분리해 둔다)

## 4. 핵심 로직 정의

BE가 월요일부터 바로 구현할 수 있도록 식으로 적는다. 예시는 돈까스집 기준.

### 4.1 이론 소비량

```
일 소비량(재료 i, 날짜 d) = Σ_메뉴 m [ 판매량(m, d) × 레시피량(m, i) ]
```

예: 돈까스 40인분 × 등심 150g = 6kg

### 4.2 추정 재고

```
추정 재고(i, 오늘) = 마지막 실사량(i)
                   + Σ 입고 확인량(i, 실사일 이후)
                   − Σ 일 소비량(i, 실사일 이후 ~ 오늘)
```

음수면 0으로 보정하고 `needs_count = true` 플래그. 실사를 다시 입력하면 기준점이 갱신된다.

### 4.3 예측

이 절의 옛 식은 지웠다. 예측 방식의 현재 결정은 DECISIONS #91, 흐름은 [설계 5.2절](2026-10-14_자동세팅_입고_예측_설계.md).
요일 평균 식의 정본은 코드 `ForecastService` · `DowAverage` (설계 5.2절에는 요일 평균 식이 없다). 예측 소비량 = Σ 메뉴 예측 판매량 × 레시피량은 `RecommendationService`.

### 4.4 발주 판단

이 절의 옛 식(안전재고 = 7일 평균 × N 만)은 지웠다. 안전재고는 [설계 5.3절](2026-10-14_자동세팅_입고_예측_설계.md) · DECISIONS #28, 발주점 · 발주 여부와 L · R 을 거래처 배송 일정으로 세는 규칙은 설계 5.4절 · DECISIONS #89.
식의 정본은 코드 `SafetyStockCalculator` · `OrderCalculator` · `DeliverySchedule` — 설계 5.3 · 5.4절에 없는 세부(σ 구간 28일 · 휴무일 제외 · 보관 방식 모르면 z 1.65 등)는 코드가 맞다.

### 4.5 발주량

```
목표 재고   = 안전재고 + Σ 예측 소비량(i, 오늘+1 … 오늘+L+R)
필요량      = 목표 재고 − 재고 포지션
발주량      = MOQ 이상으로 올림 → 포장 단위 배수로 올림 → 품목별 최대 발주량 이하로 자름
```

예: 필요량 18kg, 포장 10kg → 20kg. MOQ 30kg이면 30kg.

### 4.6 추천 이유 문장

템플릿으로 생성한다. LLM 없음.

```
"현재 추정 재고 {est}kg, 입고 예정 {on_order}kg.
 배송까지 {L}일간 예상 소비 {ltd}kg, 안전재고 {ss}kg.
 {exhaust_date} 소진 예상. 오늘 주문하면 {arrival_date} 도착."
```

### 4.7 주문 메시지

거래처별 템플릿 한 개. 발주한 품목을 묶어서 렌더링. 완성된 메시지는 보냄을 누르면 카카오톡 공유(카카오 JS SDK 텍스트 템플릿)로 넘기고 보냄으로 표시한다. 200자 초과 · 키 없음 · SDK 실패면 폰은 공유 시트(Web Share API), 데스크톱은 복사. 보냄은 취소할 수 있고, 시트를 닫을 때 보냄인 거래처만 발주로 저장한다(DECISIONS #49 · #79).

```
안녕하세요, 위글리입니다.
{arrival_date} 배송으로 아래 부탁드립니다.
- {product_name} {qty}{unit}
- ...
감사합니다.
```

템플릿은 거래처 설정 화면에서 사장님이 수정 가능. 미팅에서 받아온 실제 카톡 주문 문구를 초기값으로 쓴다.

### 4.8 가격 연동 (비쌀 때 적게·자주, 쌀 때 많이·드물게)

이 절의 옛 식은 지웠다. 가격 지수 · R' 배수는 [가격 지수 정의](2026-10-15_가격지수_정의.md) 1 · 2절, 조정한 R'로 목표 재고 · 발주량을 내는 식은 [설계 5.4절](2026-10-14_자동세팅_입고_예측_설계.md), 유통기한 상한은 DECISIONS #28.
조정은 발주 주기 R에만 걸고 안전재고 · 발주점은 건드리지 않는다. 쌀 때도 유통기한 상한과 `max_order_qty`(1회 최대)를 넘지 않는다. 재료별 `price_sensitive`로 끌 수 있다.
식의 정본은 코드 `PriceIndexCalculator` · `OrderCalculator`.

## 6. 화면

탭 6개(홈 · 발주 · 발주 이력 · 레시피 · 거래처 및 재료 · 더보기, DECISIONS #61). 프로토타입 `docs/design/prototype/app_all.html`(DECISIONS #60)이 기준이다. 화면 이름은 폰과 데스크톱이 같다.

> DECISIONS #61 ~ #64 · #72 로 바뀐 점: 홈은 인사말 옆 이번 주 매출 예측 카드 + 큰 버튼 두 개(오늘 발주 추천 품목 · 오늘 입고 예정 품목), 발주 카드를 누르면 추천 품목이 담긴 채 발주 탭으로 넘어간다. 발주 탭은 추천 품목 목록 → 품목 드롭다운(발주량 · 8주 단가 · 주문처 표에서 담기) + 오른쪽 매출 예측 카드 · 거래처별 발주 목록이고, 7일 타임라인 · 보류 · 충분한 재료 · 발주 달력은 뺐다(#72). 입고 탭은 발주 이력 탭(오늘 입고 예정 + 월별 거래 내역)으로 바뀌고 입고 확인 · 영수증 · 확인 목록은 화면에서 빠졌다. 발주는 담을 때 고른 주문처별 주문 메시지 → 보냄(쇼핑몰은 주문 완료)인 줄만 시트를 닫을 때 발주로 저장한다(#79). 아래 1 · 2항과 다르면 결정 쪽이 맞다.

1. **발주 (홈).** 헤더 아래 가게 설정 띠("가게 설정 N개 남음", 다 채우면 사라짐 · #50) → 오늘 주문 목록(행마다 발주 · 보류 · 수량 스테퍼. 발주한 행은 발주 취소) → 이번 주 주문 달력(7일, 세로) → 충분한 재료(접힘). 품목 상세(폰은 행 펼침, 데스크톱은 오른쪽 상세 카드): 7일 타임라인, 근거 표, 단가 배지("최근 8주보다 +12%") · 8주 추이 · 식봄 표시가(#48. 쿠팡은 수집 불가라 3주 범위에서 뺌, DECISIONS #68). 하단 바 "모두 발주" → 확인 → 거래처별 메시지 시트 → 공유(#49). 입고 처리는 홈에 두지 않는다.
2. **입고.** 영수증 올리기(OCR) → 확인 목록(상품명 → 재료, 단위). 입고 예정 목록: 영수증이 맞으면 자동으로 입고 확인, 없으면 "입고 확인" 버튼(받은 양 · 단가). 최근 발주(추천값 vs 최종값). 실사일 이전 영수증은 "재고 미반영"으로 표시. 예측 정확도 표는 없다(#51).
3. **레시피.** 메뉴 목록(사진 · 이름 · 가격 · 재료 수, #45) → 메뉴를 누르면 그 메뉴의 재료 × 1인분 양. 재료 추가는 시트에서(재료 고르기 또는 새 이름, 양, 단위).
4. **거래처 및 재료.** 거래처 행(펼치면 주문 방법 · 마감 · 배송 기간 · 주문 간격 · 배송 요일 · 최소 주문금액 · 메시지 템플릿). 재료는 폰에서 줄 목록(이름 · 추정 재고, 아래 안전재고 · 단가), 데스크톱은 표. 행을 누르면 편집 시트(안전재고 일수 · 1회 최대 · 거래처 상품 · 단가, #52).
5. **더보기.** 가게 정보(상호명 · 화면 이름 · 위치, 보기만. 위치는 네이버 플레이스 전체 주소 → 시군구 → `–`, DECISIONS #115), POS 업로드(엑셀 올리기 → 반영 완료 · 지난 업로드. 메뉴 연결은 뺐다, DECISIONS #80), 가격 비교 켬/끔, 가게 설정(온보딩에서 남은 단계), 로그아웃.

탭 밖: 로그인, 회원가입(약관 동의, #46), 온보딩 3단계(가게 찾기 → 메뉴 분석 → 레시피 확인).

설명 문구는 넣지 않는다(예외: 레시피 탭 "레시피를 확인해주세요!" 한 줄, DESIGN.md 레시피 탭). 제목, 숫자, 컨트롤, 짧은 상태 단어만. 상태 · 빈 목록 · 버튼은 명사형("주문 없음", "발주 25 kg", "모두 발주"). 확인이 필요한 것은 행이 아니라 그 칸만 표시한다. 모바일 우선, 사장님은 폰으로 본다.

## 7. API 최소 목록

처음 잡은 목록이다. 지금 있는 주소 전부와 요청 · 응답 상세의 정본은 서버 Swagger, 공통 계약은 [API.md](../API.md). 컨트롤러에 없는 주소는 "미구현"으로 표시했다.

CRUD  /menus  /ingredients  /recipes  /suppliers  /supplier-products

PATCH /recommendations/{id}                    {action: approve|modify|reject, finalQty, reason}

GET   /purchase-orders                                                          미구현
PATCH /purchase-orders/{id}/items/{itemId}/receive   {receivedQty, unitPrice}

## 8. 안전장치

실제 주문으로 이어지므로 3주 안에도 뺄 수 없는 것.

- recommendation은 (store_id, ingredient_id, run_date) unique. 하루 한 재료 한 건
- 상태 전이는 PENDING → APPROVED 또는 REJECTED 한 번만. 다시 바꾸려면 새 추천
- 품목별 max_order_qty 초과 시 추천 수량을 자르고 경고 표시
- 승인자와 시각 기록
- 모든 조회·쓰기는 로그인한 계정의 store_id로 강제. 다른 가게의 id를 URL에 넣었을 때 보이면 버그. 통합 테스트에 가게 2개를 넣어 확인한다
- 가격 조정은 R'에만. 안전재고·발주점은 불변. 쌀 때 상한은 유통기한과 max_order_qty. 단가 이력이 3건 미만이면 조정 없음
- (조건부 Level 2) 전송 직전 재검증, 전송 로그, 실패 사유 저장, 재시도 1회

## 9. 1주차에 실데이터가 없을 때

Data/AI 담당이 샘플 데이터를 만든다.

- 메뉴 8개, 재료 12개, 거래처 3곳
- 730일치(2년) 일별 판매량. 요일 패턴 (금·토 1.4배) + 월별 계절 배수 · 완만한 성장 + 공휴일 · 가상 지역 행사 + 정규 노이즈 + 월 2회 임의 휴무 · 설 · 추석 당일 휴무 (S15P31A308-162)
- 레시피는 돈까스집 기준 가상값

실데이터가 오면 같은 업로드 경로로 교체한다. 샘플 데이터 스크립트는 이후에도 테스트 데이터로 쓴다.

## 10. 리스크

| 리스크 | 징후 | 대응 |
|---|---|---|
| 사장님 데이터가 1주차 안에 안 옴 | 미팅 연기, 포스 export 불가 | 샘플로 진행. 미팅은 이번 주 안에 반드시. 포스 export 불가 시 관리자 화면 캡처 → 수기 입력 |
| 레시피 작성이 늦어짐 | 사장님 시간 못 잡음 | 주력 메뉴 3개만 먼저. 나머지 재료는 추천 대상에서 제외 |
| 포스 메뉴명이 지저분함 | 같은 메뉴가 여러 이름 | 매핑 화면에서 사용자가 합침. 자동화하지 않는다 |
| 추정 재고가 실제와 많이 다름 | 사장님이 매번 수량 수정 | 실사 재입력. 안전재고 N 상향. 4주차에 보정계수 |
| 3주차에 Level 2까지 하려다 Level 1이 흔들림 | 3주차 중반까지 승인 플로우 미완 | Level 2는 즉시 드롭. Level 1 완성이 우선 |
| 거래명세서에 단가가 없음 | 입고 확인에 단가를 못 적음 | 가격 지수 = 1로 두고 평소대로 발주. 거래처 상품 단가를 사장님이 월 1회 갱신. 4주차에 외부 시세로 보강 |
| 멀티 테넌트 때문에 1주차가 늦어짐 | 로그인·스코프에 3일 이상 | 가입·권한은 최소(계정 1, 역할 OWNER만). 스코프 강제는 미들웨어 한 곳. 그 이상은 4주차 |
