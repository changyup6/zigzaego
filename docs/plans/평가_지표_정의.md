## 2. 레시피 자동 세팅

### 2.1 재료 구성 F1

**무엇**: LLM이 뽑은 "이 메뉴에 이 재료가 들어간다"가 실제 레시피와 얼마나 맞나. 양은 보지 않는다.

```
쌍 = (메뉴, 재료).  예측 쌍 P = 구성 추출 결과를 recipe 행으로 펼친 것 (질문 답변 전)
                    정답 쌍 T = 위글리 실제 레시피
TP = |P ∩ T|,  FP = |P − T|,  FN = |T − P|
정밀도 = TP / (TP + FP),  재현율 = TP / (TP + FN),  F1 = 2 · 정밀도 · 재현율 / (정밀도 + 재현율)
```

- **micro 평균**: 메뉴별 F1을 평균하지 않고 모든 메뉴의 쌍을 한꺼번에 센다. 재료가 많은 메뉴가 더 무겁다
- **시점**: 질문에 답하기 전, 조합 규칙(파스타볼 = 소스 × 단백질 + 토핑)을 recipe 행으로 펼친 직후. 답변이 들어간 뒤는 2.3에서 잰다
- **제외**: 소스 원재료와 주기형 품목은 양쪽에서 뺀다(설계 2.6 · 4.1). 소스 자체(예: 까르보나라 소스)는 하나의 재료로 센다
- **이름 맞추기**: 같은 재료 · 메뉴의 다른 표기(불고기 = 소불고기, 생크림 = 휘핑크림)는 정답표에 별칭 열을 두고 맞춘다. 별칭에도 없으면 다른 것이다
- **정답에 없는 메뉴**는 양쪽에서 빼고 개수만 보고한다. 분모가 0이면 그 항(정밀도 · 재현율 · F1)은 0으로 둔다
- 메뉴별 F1도 같이 보고한다. 평균은 넘었는데 특정 메뉴만 크게 틀린 경우를 찾기 위해서다

### 2.2 질문 수

```
질문 수 = 한 번의 온보딩 job이 만든 객관식 질문 개수
기준 = 메뉴 수 ≤ 30 이면 10개 이하, 30 초과면 10 × 메뉴 수 / 30 이하 (30 초과 비례는 8절에 없는 해석)
```

질문 하나가 여러 메뉴에 걸리면(예: 파스타 면 1인분) 1개로 센다.

### 2.3 답변 후 1인분 MAPE

**무엇**: 질문에 답한 뒤 저장된 1인분 양이 실제와 얼마나 가까운가.

```
대상 = 예측과 정답에 모두 있는 (메뉴, 재료) 쌍 중 BOM 품목
MAPE = 평균 ( |예측 1인분 − 정답 1인분| ÷ 정답 1인분 )
```

- 양쪽 다 DB 기준 단위(G · ML · EA)로 바꾼 뒤 비교한다. 단위가 다르면(개 ↔ g) 맞출 수 없으므로 **틀린 것(오차 100%)**으로 센다
- 한쪽에만 있는 쌍은 여기서 보지 않는다. 2.1 F1이 잡는다
- 1:1 품목은 1인분이 항상 1이라 뺀다
- **답변**: 사장님이 실제로 고른 답(S15P31A308-13 미팅의 질문 답변)을 넣는다. 평가하는 사람이 정답에 가까운 선택지를 고르지 않는다
- 정답이 0인 쌍은 MAPE에서 빼고 가중 오차에만 넣는다. 대상 쌍이 0개면 "측정 불가"로 적는다
- 정답이 아주 작은 값(예: 소금 2g)은 MAPE를 크게 흔든다. 같이 **가중 오차** Σ\|예측 − 정답\| ÷ Σ정답도 보고한다

### 2.4 소요 시간

```
소요 시간 = job.status 가 DONE 이 된 시각 − job 생성 시각
```

같은 가게로 3번 돌려 **가장 긴 값**을 기준과 비교하고 중앙값도 같이 적는다. Apify 수집 시간이 매번 달라서다. 단계별(수집 · 구성 추출) 시간도 같이 적는다.

## 3. 영수증 OCR

### 3.1 줄 정확도

**무엇**: 사진 한 장에서 품목 줄을 얼마나 정확히 읽나.

```
정답 줄   = 영수증마다 사람이 적은 (품목명, 수량, 단가)
맞은 줄   = 예측 줄 중 정답 줄과 짝지어졌고, 품목명 · 수량 · 단가가 모두 같은 줄
줄 정확도 = 맞은 줄 ÷ 정답 줄 수
```

- **짝짓기**: 영수증 안에서 예측 줄과 정답 줄을 1:1로 맞춘다. 품목명 글자 유사도(편집 거리)가 가장 높은 쌍부터 짝짓는다. 짝이 없는 정답 줄은 틀린 것이다
- **같다의 기준**: 품목명은 공백 · 괄호 기호 · 대소문자를 지우고 비교한다(괄호 안 글자는 남긴다: `돈등심(국내산)` → `돈등심국내산`). 수량 · 단가는 숫자가 정확히 같아야 한다(쉼표 · 원 표기는 지운다)
- 정답에 없는 줄을 지어낸 경우(합계 줄을 품목으로 읽음 등)는 분모에 넣지 않고 **추가 줄 비율**(추가 줄 ÷ 예측 줄)로 따로 적는다
- 인쇄 영수증과 손글씨(거래명세서 수기)는 **따로** 계산한다. 기준 90%는 인쇄에만 적용한다
- 같은 20장으로 CLOVA + LLM 경로와 멀티모달 LLM 단독을 둘 다 재서 나은 쪽을 쓴다(8절 "미달 시")

### 3.2 매칭 정확도

**무엇**: 처음 보는 상품명을 어느 재료로 연결하나.

```
대상      = 3.1에서 짝지어진 줄 (사전을 비우고 시작하므로 전부 "사전에 없던 줄"). OCR이 놓친 줄은 분모 밖
맞은 줄   = LLM이 제안한 재료가 정답 재료와 같은 줄 (정답이 "주기형 새 품목"이면 새 주기형 후보로 분류한 줄)
매칭 정확도 = 맞은 줄 ÷ 대상 줄
```

- 사전을 비운 상태에서 20장을 순서대로 넣는다. 사장님 확인으로 사전이 쌓이는 효과는 빼고, LLM 제안 자체만 잰다
- 포장 변환(1단 → 1000g)이 맞았는지는 별도 비율로 보고만 한다. 기준에는 넣지 않는다

## 4. 수요 예측

### 4.1 WAPE · Bias

```
WAPE = Σ|실제 − 예측| ÷ Σ실제
Bias = Σ(예측 − 실제) ÷ Σ실제        + 면 많이 예측(과잉 발주), − 면 적게(품절 위험)
```

모든 행을 한꺼번에 합친다(pooled). Σ실제 = 0이면 nan. 코드: `ai/src/weglee_ai/metrics.py`. MAPE를 쓰지 않는 이유는 하루 판매가 0 · 1개인 메뉴에서 값이 폭발하기 때문이다.

### 4.2 평가 방식 — rolling origin

```
평가 기간의 날짜마다(= 기준일 t)
  t일까지의 데이터만으로 t+1 ~ t+7 을 예측한다
  예측과 실제를 (날짜, 채널, 메뉴) 단위로 비교한다
```

- **h = 1(다음 날)을 기준 지표**로 한다. 서비스 추천은 03:00 예측을 그날 쓴다
- h = 1~7 평균도 같이 보고한다. 리드타임 · 발주 주기 동안의 소비 예측에 쓰이기 때문이다. 현재 `baseline.rolling_forecast`는 h = 1만 지원 — h = 1~7은 S15P31A308-78 · 57에서 확장
- **단위**: (날짜, 채널, 메뉴)에서 계산하고, 채널을 더한 (날짜, 메뉴)도 같이 낸다. 재료 소비로 이어지는 건 채널 합이다
- **행 없는 날**: [판매 데이터 사전 5절](../data/판매_데이터_사전.md) — 휴무는 빼고, 영업일 미판매는 0으로 넣는다(`baseline.fill_daily`)
- **평가 기간**: 마지막 8주. 그 앞은 학습 · 이력으로만 쓴다. 현재 `01_baseline_wape.ipynb`는 4주(`EVAL_WEEKS = 4`) — 백테스팅 비교표(S15P31A308-57)에서 8주로 맞춘다
- ~~**비교 규칙**: 같은 평가 기간 · 같은 행에서 TimesFM WAPE < 요일 평균 WAPE이면 TimesFM 채택. Bias ±10%는 **채택된 모델**의 별도 합격 조건 — 넘으면 채택 보류하고 원인(과대 · 과소)을 보고~~
- **위 비교 규칙은 폐기** ([DECISIONS #91](../DECISIONS.md)). TimesFM 은 서비스 예측에 쓰지 않고, 발주 추천의 수요 예측은 최근 4주 같은 요일 평균(휴무일 제외)이다. 매출 예측 모델의 기준은 그 모델 문서에서 정한다(S15P31A308-225 · 226). 4.1 식과 이 절의 평가 방식(rolling origin · h · 단위 · 행 없는 날)은 요일 평균을 잴 때 그대로 쓴다

### 4.3 정답 데이터

위글리 배달 이력 중 **홀 개업 전 기간**(설계 5.2). 홀 이력은 2주뿐이라 평가하지 않는다. 실데이터 전에는 `ai/data/sample/`로 식이 도는지만 확인한다.

## 5. 안전재고 시뮬레이션

**무엇**: 같은 과거 소비를 두 안전재고 식으로 다시 돌려 봤을 때 어느 쪽이 덜 떨어지고 덜 버리나.

```
재료마다, 평가 기간의 날마다
  아침: 도착할 입고를 더한다
  발주: 설계 5.4 그대로 — 재고 + 입고 예정 ≤ ROP 이면 S − 재고 − 입고 예정, 포장 올림 · MOQ · 유통기한 상한
  하루: 실제 소비(판매 × 레시피)를 뺀다. 오래된 입고분부터 쓴다(FIFO)
  밤: 입고일 + 유통기한을 넘긴 남은 양을 버린다

SS 기존 식 = 최근 7일 평균 소비 × N일           (DECISIONS #10)
SS 통계식  = z × σ × √(R + L)                    (설계 5.3, z는 보관 방식별, 소비 이력 28일 미만이면 기존 식)

파라미터: σ = 그날 이전 28일 일 소비 표준편차 · R · L = supplier 값 · 시작 재고 = 첫날 목표 재고 S(유통기한은 첫날부터)
폐기 경계: 입고일 + 유통기한일이 지난 밤에 남은 양을 버린다 (유통기한 5일 → 입고 5일째 밤까지 사용 가능)
```

| 지표 | 식 |
|---|---|
| 품절 일수 | 그날 소비를 다 채우지 못한 날 수 (재고 < 소비) |
| 폐기량 | 유통기한을 넘겨 버린 양의 **금액 합계**(입고 단가). 수량(기준 단위)은 재료별 참고 |

- 예상 소비는 두 식 모두 **같은 예측(요일 평균)**을 쓴다. 안전재고 식의 차이만 보기 위해서다
- 주기형 품목은 두 식이 같으므로(소비 이력 28일 미만 · 주기형 = 기존 식, 설계 5.3) 빼고 BOM · 1:1만 비교한다
- 기준: 핵심 재료 합계(품절 = 재료 × 일 수, 폐기 = 금액)에서 **통계식이 둘 다 기존 식 이하**. 재료별 결과도 같이 낸다
- 샘플 데이터의 `true_stock.csv`는 시뮬레이터가 맞게 도는지 확인하는 데 쓴다
