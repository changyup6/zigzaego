# 영수증 업로드 API 제안 (구현됨 → [docs/API.md](../API.md) 8절)

기준일: 2026-10-19 · 지라 S15P31A308-111 · 상위 문서: [자동 세팅 · 사진 입고 · 예측 설계](2026-10-14_자동세팅_입고_예측_설계.md) 4.2 · 4.4 · 4.5절 · DECISIONS #27 · #32 · #34 · #35 · #41

**제안과 달라진 점** (코드 `purchasedoc/controller/ReceiptController` 기준, 상세는 Swagger): `GET /receipts` 응답에 `matches` · `options` 와 함께 확정만 남은 영수증 `readyDocs` 가 붙는다. `files` 는 CONFIRMED 가 아닌 장 전부 + CONFIRMED 는 올린 지 7일 안. 읽기 전에 멈춘 장도 `fail`, `error` 는 job 사유 또는 `RECEIPT_INTERRUPTED`. `GET /receipts/{docId}` 의 줄에 `id` · `status` 가 더 있다. 요청 한 번은 20MB 까지이고 화면이 나눠 보낸다(요청마다 job 하나, 넘으면 400 `COMMON_INVALID_INPUT`). CLOVA 키가 없으면 `RECEIPT_ALLOW_FAKE_OCR=true` 일 때만 올리기 · 다시 읽기가 열리고 기본은 503 `RECEIPT_OCR_NOT_CONFIGURED`. 지우기는 문서 · 줄 행만 지우고 원본 파일은 남긴다(#34). 사장님이 정한 줄이 있어도 409 `RECEIPT_ALREADY_CONFIRMED`, 읽는 중이면 409 `RECEIPT_IN_PROGRESS`.

지라 111 의 영수증 처리 job 은 서비스(`ReceiptJobService.start`)까지 만들어 두었다(가지 `be/feat/receipt-upload-job-S15P31A308-111`). **바깥에서 부르는 HTTP 주소는 이 문서로 BE · FE 컨펌을 받은 뒤** 붙인다. API.md 에 아직 영수증 절이 없고, 화면은 목(`frontend/src/lib/mock/receipts.ts`)으로 돌고 있어서 그 모양에 맞춰 제안한다.

**리뷰 요청**: BE-1(BE · 주소 · 오류 코드), PM·FE(FE · 응답 모양 · 화면 상태). 아래 "정할 것" 에 답을 달아 주시면 그대로 API.md 에 옮기고 주소를 붙인다.

## 1. 주소

| Method | URL | 하는 일 | FE 목 함수 |
|---|---|---|---|
| POST | `/receipts` | 영수증 여러 장 올리기 → job 시작 | `uploadReceipts` |
| GET | `/receipts` | 내 가게 영수증 장 목록 (2초 폴링) | `getReceipts` · `pollReceipts` |
| GET | `/receipts/{docId}` | 한 장과 읽은 품목 줄 | (상세 화면 생기면) |
| POST | `/receipts/{docId}/retry` | 실패한 장 다시 읽기 | `retryReceipt` |
| DELETE | `/receipts/{docId}` | 확인 전 장 지우기 (원본 파일 포함) | `removeReceipt` |

확인 목록(`matches` · `confirmMatch`)과 사장님 확인 반영은 112 · 113 에서 같은 `GET /receipts` 응답에 붙인다. 이번 제안은 장(`files`) 부분만.

모두 로그인 필수, 내 가게 것만. 남의 가게 `docId` 는 404(존재 여부를 드러내지 않음 — 기존 `PurchaseDocService.getForStore` 규칙).

## 2. 요청 · 응답

### POST /receipts

`multipart/form-data`, 필드 `files` 여러 개. 검사는 서비스에 이미 있다(`ReceiptJobErrorCode`).

| 검사 | 응답 |
|---|---|
| 장 수 0 | 400 `RECEIPT_FILE_REQUIRED` |
| 50장 초과 | 400 `RECEIPT_TOO_MANY_FILES` |
| 한 장 10MB 초과 | 400 `RECEIPT_FILE_TOO_LARGE` |
| JPG · PNG · PDF 밖 | 400 `RECEIPT_FILE_NOT_SUPPORTED` |

하나라도 걸리면 전체 거절(아무것도 저장하지 않음). 통과하면 `202` + 아래 목록과 같은 모양(FE 가 올린 직후 바로 목록을 그림).

요청 크기: 지금 서버 전체 상한이 20MB(`application.yaml` `spring.servlet.multipart`)라 50장 × 10MB 를 한 번에 못 받는다. 영수증 주소만 올릴지(최대 500MB), FE 가 20MB 씩 나눠 보낼지 정해야 한다(4절 2번).

### GET /receipts

```json
{
  "jobId": "42",
  "files": [
    { "id": "101", "file": "IMG_2031.jpg", "at": "2026-10-19T08:12:00+09:00",
      "st": "done", "kind": "RECEIVE", "docDate": "2026-10-18", "lineCount": 7, "error": null },
    { "id": "102", "file": "IMG_2033.jpg", "at": "2026-10-19T08:12:00+09:00",
      "st": "fail", "kind": null, "docDate": null, "lineCount": 0, "error": "RECEIPT_NO_ITEMS" }
  ]
}
```

- `st` 는 FE 목의 `ReceiptStatus` 그대로: DB `parse_status` PENDING → `wait`, PROCESSING → `read`, PARSED · CONFIRMED → `done`, FAILED → `fail`.
- `kind`: `PAST`(재고 확인일 이전 → 재고 미반영) / `RECEIVE` / `null`(날짜 못 읽음).
- `jobId`: 가장 최근 업로드 job. 진행 중이면 FE 는 `GET /receipts` 만 2초마다 부르면 된다(`GET /jobs/{id}` 는 몰라도 됨).
- `at` 은 ISO 시각, id 는 문자열(API.md 규칙). 목은 "10/6 08:12" 글자라 표시 형식은 FE 가 만든다.

### GET /receipts/{docId}

장 하나 + 줄 목록 `lines: [{ lineNo, rawName, qty, unit, unitPrice, amount, ingredientId, confidence }]` + 읽은 거래처 이름 `supplierName`. 111 이 사전 매칭 · LLM 매칭 제안까지 줄에 채운다(확정은 112).

### POST /receipts/{docId}/retry · DELETE /receipts/{docId}

- retry: `fail` 인 장만. 아니면 409 `RECEIPT_NOT_FAILED`. 새 job 으로 그 장만 다시 읽는다. 응답은 `GET /receipts` 와 같은 모양.
- delete: 사장님이 확인(`CONFIRMED`)하기 전 장만. 아니면 409 `RECEIPT_ALREADY_CONFIRMED`. 행 · 줄 · 원본 파일을 지운다. 응답은 `GET /receipts` 와 같은 모양.

## 3. 처리 규칙 (job · 서버 안, 111 구현 그대로)

- 원본은 `app.receipt.storage-dir`(기본 `./data/receipts`, 운영 `/data`) 아래 `{storeId}/{jobId}/{uuid}.{jpg|png|pdf}` (DECISIONS #34). DB 에는 경로만.
- 장마다 순서대로: CLOVA General OCR(호출 사이 1초) → LLM 정형화(110 `normalize` 프롬프트) → 상품명 사전(`supplier_product`) 매칭 → 사전에 없는 줄만 LLM 매칭(110 `match` 프롬프트) → `purchase_doc_line`(PENDING).
- 한 장이 실패해도 다음 장 계속. 장별 실패 사유는 OCR · LLM 오류 코드, `RECEIPT_NO_ITEMS`, `RECEIPT_FILE_MISSING`. **모든 장이 실패하면 job 도 FAILED**(`RECEIPT_ALL_FAILED`).
- `kind`: 문서 날짜 < 가게의 가장 최근 재고 확인 날짜(`stock_count.counted_at` 최댓값, 가게 시간대) → `PAST`, 같거나 이후 → `RECEIVE`, **재고 확인 기록이 없으면 `RECEIVE`**, 날짜 못 읽으면 `null`.
- **CLOVA 키가 아직 없다.** 키(`CLOVA_OCR_URL` · `CLOVA_OCR_SECRET`)가 비어 있으면 서버는 정해진 가짜 OCR 결과를 쓰고 `ocr_json` 에 `fake=true` 를 남긴다. 그래서 **주소는 CLOVA 키가 들어온 뒤에 연다** — 그 전에 열면 사장님 화면에 가짜 품목이 뜬다(4절 4번).

## 4. 정할 것

1. **주소 이름 · 모양** — `/receipts` 아래 5개, 목록 응답이 FE 목의 `files` 모양(위 2절)이면 되나? (규리 · 태정)
2. **한 번에 올리는 양** — 서비스 상한은 50장 · 장당 10MB · JPG/PNG/PDF. 요청 크기 상한을 영수증 주소만 500MB 로 올릴지, FE 가 20MB 씩 나눠 보낼지. (규리 · 태정)
3. **재고 확인 기록이 없을 때** — 지금 구현은 `RECEIVE`(재고에 더하는 쪽). 가입 첫날 올린 과거 영수증이 재고에 더해지는 게 맞나, `PAST` 로 바꿀까? (태정)
4. **여는 시점** — CLOVA 키가 오기 전에는 주소를 열지 않는다(가짜 OCR 방지). 그 전에 FE 연결 시험이 필요하면 개발 서버에서만 열지. (규리 · 태정)
