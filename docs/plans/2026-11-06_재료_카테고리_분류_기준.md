# 재료 카테고리 분류 기준

지라 S15P31A308-273(표 · 칸 추가) · 274(자동 분류) · 275(카테고리 CRUD). 재료 탭이 냉장고 · 선반 · 창고 그림 안의 재료를 **육류 · 채소 · 과일 · 소스**처럼 걸러 보이기 위해, 재료마다 카테고리 하나를 붙인다. 결정은 [DECISIONS #77](../DECISIONS.md), 표는 [ERD `ingredient_category`](../design/erd.md).
기본 목록의 정본은 `backend/.../ingredient/entity/DefaultIngredientCategory.java` 이고 `V11__ingredient_category.sql` 의 VALUES 는 그 복사본이다. 이 문서는 **왜 11종인지, 애매한 재료를 어디에 두는지, 품목군 표와 어떻게 이어지는지**를 적는다.

### 2.1 나누는 기준 — 애매할 때 이렇게 정한다

1. **사장님이 가게에서 어디에 둘지 떠올리는 묶음**이 기준이다. 영양학 분류가 아니다. 그래서 콩나물은 채소가 아니라 두부·콩, 버섯 · 마늘 · 허브는 채소.
2. **가공 단계가 바뀌면 카테고리도 바뀐다.** 돼지고기는 육류, 햄 · 소시지는 가공식품. 고등어는 수산, 어묵은 가공식품. 과일은 과일, 과일 잼은 양념·소스.
3. **마시는 것은 전부 음료.** 우유만 예외로 계란·유제품(요리 재료로 쓰는 쪽이 많다).
4. **기름 · 설탕 · 소금 · 향신료 · 가루 양념은 양념·소스.** 밀가루 · 전분 · 빵가루처럼 "양을 이루는 가루"는 곡물·면·떡.
5. **김치는 가공식품.** 직접 담근 것도 배추(채소)와 보관 자리가 다르다.
6. 1~5로 못 정하면 **기타**. 억지로 넣지 않는다 — 사장님이 275 로 바꾸면 그 값이 우선이고 자동 분류가 덮어쓰지 않는다.
7. 11종에 없는 묶음이 가게에 필요하면 사장님이 새 카테고리를 만든다(275). 기본 목록에 더할지는 여러 가게에서 같은 요구가 나올 때 다시 본다.

## 4. 저장 · 동작 규칙

- `ingredient_category`: `id` · `store_id` · `code`(기본 11종 코드, 사장님이 만든 것은 NULL) · `name`(가게 안 unique) · `sort_order`(기본 1~10 · 기타 99) · `created_at`. `(store_id, code)` unique.
- `ingredient.category_id` NOT NULL. DB 기본값 없음 — 넣는 쪽이 명시한다(`storage_location` 과 같은 원칙).
- 가게가 생기면 기본 11종을 바로 넣는다(`IngredientCategoryService.seedDefaults`, 기존 가게는 V11). 그래서 "기타가 없는 가게"는 없고, 있으면 데이터가 깨진 것이라 예외.
- 재료가 생기는 세 경로 — `POST /ingredients` · 온보딩 확정(`RecipeSetupService`) · 영수증 주기형(`ReceiptConfirmService`) — 는 카테고리를 정하지 않으면 그 가게의 기타.
- 응답: `GET /ingredients` · `GET /ingredients/{id}` 의 `category {id, name, code}`. `code` 는 기본 11종이면 그 코드, 사장님이 만든 것은 null — 이름은 바뀔 수 있으니 '기타' 판별 · 아이콘은 `code` 로. Swagger 가 정본.
- 자동 분류는 5절. 카테고리 CRUD · `PATCH /ingredients/{id}` `categoryId`(고르면 `category_source = OWNER`)는 [API.md 11절](../API.md) · DECISIONS #82 (275).

## 5. 자동 분류 (S15P31A308-274)

재료가 생기는 세 경로(`POST /ingredients` · 온보딩 확정 · 영수증 주기형)가 이름으로 카테고리를 정한다. 구현은 `IngredientCategoryClassifier`, 결정은 [DECISIONS #78](../DECISIONS.md).

| 순서 | 어디서 | 어떻게 |
|---|---|---|
| 1 | 백업 파일 `INGREDIENT_CATEGORY_BACKUP_DIR/ingredient_categories_latest.csv` | 같은 (가게 이름, 재료 이름)이 있으면 그 값. DB 를 새로 만들었을 때 LLM 을 다시 부르지 않는다 |
| 2 | 범용 재료표 `onboarding/ingredient_catalog.csv` | 이름 · 별칭이 같으면(공백 · 대소문자 무시) `ingredient/catalog_category.csv` 의 코드. 재료표 76종마다 한 줄 — 2절 기준으로 손으로 정했고 테스트가 빠짐을 막는다 |
| 3 | 품목군 표 `market_item_group` | 이름 · 별칭이 정확히 같은 품목군이 하나면 그 `category` → 3절 매핑 |
| 4 | LLM (`GMS_MODEL`, 2026-11-06 기준 `gpt-6-luna`) | 남은 이름을 40개씩, 그 가게의 카테고리 이름 목록(기본 11종 + 사장님이 만든 것)에서 하나 고르게. 프롬프트 `backend/src/main/resources/ingredient/category.md` · 응답 스키마 `category.schema.json` — 2절 기준을 그대로 적었다. 요청 하나를 `INGREDIENT_CATEGORY_LLM_TIMEOUT`(기본 20초)까지만 기다린다 |
| 5 | 기타 | 목록 밖 응답 · 응답에 빠진 이름 · LLM 실패 · 시간 초과 · GMS 설정 없음. **어떤 경우에도 재료 생성은 실패하지 않는다** |

- 출처 `ingredient.category_source`(V12): 자동 분류가 붙이면 `AUTO`, 사장님이 고르면(275) `OWNER`. 자동 분류는 `AUTO` 만 다시 분류하므로 사장님 선택이 덮이지 않는다.
- 온보딩 확정은 초안 재료 전부를 LLM 요청 1번에 묶는다. 영수증 주기형은 새 재료 이름마다 1번(드물다). `POST /ingredients` 는 1번.
- `POST /ingredient-categories/auto-assign`: 로그인한 가게에서 자동 분류로 기타인 재료만 같은 순서로 다시 분류하고 `{assignedCount, otherCount}` (옮긴 수 · 그 뒤에도 기타인 수).
- 백업 · 되살리기: 자동 분류 · auto-assign 이 커밋되면 재료 ↔ 카테고리 전체를 `ingredient_categories_latest.csv`(`store_name,ingredient_name,category_code,category_name,category_source`)에 **합쳐 쓴다** — 파일의 줄 위에 DB 의 줄을 얹되 DB 가 '자동 분류 기타'인 줄은 파일이 아는 값을 덮지 않는다(DB 를 새로 만든 뒤 첫 재료가 생겨도 아직 되살리지 않은 줄이 남는다). DB 를 새로 만들면 (1) 시드: 그 파일을 샘플 폴더(여러 가게면 `stores.csv` 옆)에 그대로 두면 ai `seed_sql.py` 가 seed.sql 에 카테고리까지 넣는다 (2) 서비스: `auto-assign` 한 번이면 1단계가 파일에서 되살린다 — 사장님이 고른 줄은 출처(OWNER)까지, 자동 분류의 기타 줄은 되살리지 않고 다시 묻는다.
- LLM 대기(묶음마다 최대 20초)는 `POST /ingredients` · `auto-assign` 에서는 트랜잭션 밖이다(분류를 먼저 하고 저장만 짧은 트랜잭션). 온보딩 확정 · 영수증 확정은 큰 확정 트랜잭션 안에서 요청 1번을 기다린다. auto-assign 은 기타 재료 40개마다 1번이라 수백 개면 수 분이 걸린다. 동시 LLM 대기는 8개까지 — 넘치면 줄을 서다 시간 제한에 걸려 기타.
- 테스트는 실제 LLM 을 부르지 않는다(`build.gradle` 이 `app.llm.key` 를 비운다 — CI 와 같은 조건). LLM 응답이 필요한 테스트는 `GmsClient` 를 가짜로 바꾼다.
- LLM 요청 · 토큰은 로그 `재료 카테고리 LLM — 재료 N개 · 입력 토큰 · 출력 토큰`, 단계별 건수는 `재료 카테고리 자동 분류 — …`.

### 5.1 샘플 30개 결과

2026-11-06, `gpt-6-luna`, 빈 DB(Testcontainers)에 가게를 하나 만들고 `POST /ingredients` 로 30개를 넣었다. 재료표 · 품목군 표에 일부러 없는 이름을 많이 섞었다.

| 결과 | 수 |
|---|---|
| 재료표 · 품목군 표로 정함 (LLM 안 부름) | 12 |
| LLM 이 정함 | 18 (요청 18번, 요청당 입력 약 875 토큰 · 출력 40~80 토큰, 1.1~1.9초) |
| **기타** | **3 / 30 (10%)** — 키친타올 · 일회용 장갑 · 숯. 전부 비식품이라 의도대로 |
| 기대와 다름 | **2 / 30** — 아래 |

| 재료 | 결과 | 기대 | 판단 |
|---|---|---|---|
| 흑마늘 | 가공식품 (LLM) | 채소 | 갈린다. 숙성 가공품으로 보면 가공식품(기준 2)이고, 마늘 자리에 두면 채소. 오분류로 세지 않는다 |
| 옥수수 전분 | 양념·소스 (품목군 표 `STARCH`) | 곡물·면·떡 | 품목군 표가 전분의 `category` 를 '양념·소스' 로 두어 3단계가 그대로 따랐다. 2절 기준 4(전분은 곡물·면·떡)와 어긋나 CSV 는 284 에서, 이미 만들어진 DB 는 V14(285)에서 '가루' 로 고쳤다 — 이제 곡물·면·떡 |

나머지 28개는 기대와 같다: 등심 → 육류(품목군), 모짜렐라 · 생강 · 호두 · 콩기름 → 재료표, 바질 페스토 · 사골육수 · 깐쇼새우 소스 · 딸기잼 → 양념·소스, 떡갈비 · 캔 참치 · 냉동 만두 → 가공식품, 냉동 블루베리 → 과일, 유부 → 두부·콩, 아메리카노 원두 · 막걸리 → 음료, 쌀국수 면 → 곡물·면·떡, 플레인 요거트 · 액란 · 메추리알 → 계란·유제품, 고등어 · 미역 · 다시마 → 수산, 표고버섯 · 청경채 → 채소.
같은 서버에서 다른 가게 토큰으로 이 재료를 조회하면 404, `auto-assign` 은 `{assignedCount 0, otherCount 3}`(기타 3개를 다시 물어도 기타).
