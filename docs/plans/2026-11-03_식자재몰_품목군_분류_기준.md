# 식자재몰 품목군 분류 · 단위 통일 기준

지라 S15P31A308-228(검색 방식 비교) · 229(사전 분류 배치). 식자재몰 상품(7개 몰, 약 48만 줄)을 **플랫폼별 최저가**와 **일별 시세 추이**로 보여 주기 위해, 상품마다 "어느 품목이고 어떤 형태이며 값을 무슨 단위로 비교하는가"를 미리 정해 두는 기준이다.
기준표의 정본은 `ai/seed/market_item_group.csv`, 읽는 코드는 `ai/src/weglee_ai/market/taxonomy.py`. 이 문서는 그 표를 **왜 그렇게 나눴고 애매한 경우를 어떻게 정하는지**를 적는다.

| 질문 | 답 |
|---|---|

| 라벨이 없으면 | 지금 규칙(`ItemMatcher` · 크롤러 `match.py`)으로 판정한다. 규칙은 지우지 않는다 |

## 2. 검색 방식 비교 — 왜 LLM 사전 분류인가

티켓 228 의 네 후보를 요건("플랫폼별 최저가 + 일별 추이, 가공품 제외, 30구 · 30EA 같은 단위 통일, 계란=달걀 · 난액=액란 같은 이명")으로 본 결론이다. 수치 비교표는 `ai/scripts/market/compare_search.py` 결과(`docs/plans/2026-11-03_검색_방식_비교_결과.md`)에 있다.

| 방식 | 이 요건에 맞는가 | 결론 |
|---|---|---|
| ① Elasticsearch + 한글 형태소 | 형태소 분석은 "계란찜"을 계란+찜으로 쪼개 **계란 검색에 더 잘 걸리게** 만든다. 211 의 Kiwi 실험과 같은 구조적 한계(진간장은 같은 품목, 양배추는 다른 품목인데 둘 다 쪼개진다). 상품에 품목군을 매겨 주지 않으므로 추이 집계에는 분류기가 따로 필요하다. 새 인프라(메모리 1~2GB, 매주 색인) | 탈락 |
| ② 벡터 검색 | 임베딩 공간에서 '계란'과 가장 가까운 것이 계란찜 · 계란말이다 — 가공품을 더 불러온다. 일반 이름(돼지고기 → 목살) 재현율에는 강하지만 그건 품목군 표의 부모 관계로 푼다 | 탈락. 뒤에 재료 이름 → 품목군 매핑 보조로 재검토 |
| ③ 앞말(prefix) 규칙 | 상품명이 브랜드 · 괄호 · ★ 로 시작해 진짜 상품 대부분을 놓친다(대파 181개 중 43, 전분 558개 중 4). 지금 규칙의 열화판 | 기준선으로만 |
| ④ **LLM 사전 배치 분류** | 상품마다 품목군 · 형태 · 수량을 한 번 매겨 두면 검색과 추이는 SQL 조인 · GROUP BY 로 끝난다. 표시 낱말 없는 가공품(홀토마토 · 깐쇼새우), 일반 이름 고기(돼지고기 → 부위), 규칙이 버리던 진짜 상품(흙대파 10단/망)을 모두 다룬다. 검색 시 비용 0 | **채택** |

212 · 213(규칙 투표 · 분류기 학습, 2026-11-02 폐기)과 다른 점: 학습 · 자동 정답 생성이 없다. LLM 이 품목군 표를 보고 바로 라벨을 매기고, 사람은 표본만 확인한다.

## 3. 품목군(item group)

### 3.1 정의

**품목군 = 사장님이 발주할 때 서로 바꿔 쓸 수 있고, 같은 기준 단위로 값을 나란히 놓을 수 있는 상품 묶음.** 최저가와 추이의 한 줄이 품목군 하나다.

같은 품목군으로 묶는 세 가지 조건을 **모두** 만족해야 한다.

| 조건 | 같은 품목군 | 다른 품목군 |
|---|---|---|
| ① 대체 가능 — 발주 목적이 같다 | 흙대파 · 깐대파 · 절단대파 → 대파 | 대파 ≠ 쪽파, 두부 ≠ 순두부 ≠ 연두부, 간장 ≠ 국간장 |
| ② 같은 가공 단계 | 생새우 · 냉동새우 · 깐새우 → 새우 | 새우 ≠ 깐쇼새우 · 새우튀김(조리) |
| ③ 같은 기준 단위로 값을 비교할 수 있다 | 계란 30구 · 계란 1.8kg(60g×30) → 계란(개) | 계란(개) ≠ 액란(g) |

### 3.2 나누는 기준 — 애매할 때 이렇게 정한다

| 상황 | 결정 | 예 |
|---|---|---|
| 품종 · 등급 · 크기 · 산지 · 브랜드 · 인증이 다르다 | **같은 품목군**. 값 차이는 "그 품목군 안의 값 폭"이다 | 특란 · 대란 · 왕란 · 유정란 · 무항생제 → 계란. 국산 · 중국산 대파 → 대파. 백다다기 · 취청 → 오이 |
| 손질만 했다(깐 · 절단 · 슬라이스 · 냉동 · 세척) | 같은 품목군, 형태는 `PREPARED` | 깐마늘 → 마늘(단, 다진 마늘은 용도가 달라 별도) |
| 익혔다 · 양념했다 · 다른 재료와 섞었다 | **가공품(`PROCESSED`)** — 어느 품목군에도 넣지 않는다 | 구운란 · 반숙란 · 계란찜 · 양념갈비 · 훈제오리 · 사과즙 |
| 말렸다 · 가루로 만들었다 | 쓰임이 달라지면 **별도 품목군** | 고추 → 고춧가루 · 건고추, 명태 → 황태, 들깨 → 들깨가루는 들깨에 포함 |
| 부위로 파는 고기 | **부위마다 품목군**, 종(돼지 · 소 · 닭)은 부모 품목군(`comparable = N`) | 돼지고기(부모) — 삼겹살 · 목살 · 앞다리살 · 뒷다리살 … 부모끼리 최저가를 비교하지 않는다(뒷다리살이 항상 이긴다) |
| 같은 이름을 두 품목군이 쓴다 | 별칭에 종을 붙여 적고, 맨이름은 **매핑하지 않는다**(이름 검색으로 넘어감) | 등심 → 소등심 · 돼지등심 |
| 액체인데 무게로 적혔다 | 같은 품목군, 밀도로 환산 | 간장 1.9kg → 1,583ml |
| 껍질을 깐 액체 계란 | **다른 품목군** — 단위도 값도 다르다 | 액란 = 난액 = 전란액 = 액상계란(g). 난백 · 난황도 액란에 둔다 |
| 포장 · 묶음 · 업소용 · 박스 | 같은 품목군. 총량으로 단위가격을 내므로 포장 단위는 무관 | 순두부 400g×40입 1박스 → 순두부 |
| 반려동물 · 주방 도구 · 화장품 | **비식품(`NONFOOD`)** | 계란 찜기 · 에그 트레이 · 개 사료(소고기맛) |
| 품목군 표에 없는 식품 | 품목군 없음(`null`), 형태만 라벨 | 깍두기 · 오란씨 |

### 3.3 품목군 표의 열

| 열 | 뜻 |
|---|---|
| `code` | 영문 대문자 코드(DB · API 에서 쓰는 안정된 키). 이름은 바뀌어도 코드는 안 바꾼다 |
| `name` | 화면에 보이는 이름 |
| `parent` | 부모 품목군 코드(부위 → 종). 부모는 `comparable = N` |
| `category` | 채소 · 과일 · 육류 · 계란 · 수산 · 유제품 · … (화면 묶음용) |
| `comparable` | `N` 이면 최저가 · 추이를 내지 않는다(부모) |
| `base_unit` | 기준 단위 `G` · `ML` · `EA` (4절) |
| `ea_weight_g` | 1개 무게(g). 개 ↔ g 환산. 비어 있으면 환산하지 않는다 |
| `density_g_per_ml` | 밀도. g ↔ ml 환산. 비어 있으면 환산하지 않는다 |
| `aliases` | 이름 · 이명 · 흔한 표기(`;` 구분). **재료 이름 → 품목군 매핑**과 **LLM 분류 대상 거르기**에만 쓴다 |
| `note` | 왜 그렇게 나눴는지 · 환산 근거 |

처음 목록은 범용 재료표(`ai/seed/ingredient_catalog.csv` 76개) + 검색 실험 34개 검색어 + 데이터셋에서 수집량이 많은 식자재(단위 혼재 조사, 6절)로 만든 182개(비교 가능 178 + 부모 품목군 4: 돼지고기 · 소고기 · 닭고기 · 치즈)다. 새 품목군은 이 표에 줄을 더하고(코드는 새로), 서비스 DB 에는 새 마이그레이션으로 넣는다.

## 4. 상품에 붙이는 라벨

LLM 배치가 **고유 상품명**마다 아래를 낸다. 같은 상품명은 어느 사이트 · 점포 · 수집일이든 같은 라벨을 쓴다(라벨의 키 = 상품명).

| 칸 | 값 | 뜻 |
|---|---|---|
| `item_group_code` | 품목군 코드 또는 `null` | 그 상품이 **원물 · 손질품으로서** 속한 품목군. 가공품 · 비식품은 `null` |
| `form` | `RAW` · `PREPARED` · `PROCESSED` · `NONFOOD` · `UNKNOWN` | 아래 표 |
| `qty` · `qty_unit` | 숫자 · `G` `ML` `EA` 또는 `null` | 상품명 · 규격에서 읽은 **전체 총량**(30구 → 30 EA, 1.8kg(60g×30) → 30 EA 가 아니라 1800 G 와 30 EA 둘 다 가능하면 기준 단위 쪽) |
| `confidence` | 0~1 | 품목군 판정 확신. 0.6 미만이면 `UNKNOWN` 취급 |
| `reason` | 짧은 글 | 왜 그렇게 봤는지(사람 표본 확인용) |
| `label_version` | 글자 | 프롬프트 버전 + 모델. 기준이 바뀌면 이 값이 바뀌고 다시 분류한다 |

| `form` | 뜻 | 최저가 · 추이에 | 예 |
|---|---|---|---|
| `RAW` | 원물 그대로 | 포함 | 흙대파, 계란 30구, 한돈 삼겹살 1kg |
| `PREPARED` | 손질 · 절단 · 냉동 · 세척만 한 원물 | 포함(화면에 '손질' 표시 가능) | 깐대파, 절단 냉동 꽃게, 손질 오징어 |
| `PROCESSED` | 익힘 · 양념 · 조합 · 음료 · 소스화 | 제외 | 계란찜, 구운란, 양념 불고기, 사과즙, 땅콩버터 |
| `NONFOOD` | 식품 아님 | 제외 | 찜기, 트레이, 사료, 세제 |
| `UNKNOWN` | 이름만으로 모름 · 확신 낮음 | 제외(건수만 보고) | "실속세트 1호" |

`item_group_code` 가 있으면 `form` 은 `RAW` 또는 `PREPARED` 뿐이다. 반대로 `PROCESSED` · `NONFOOD` 는 코드가 `null` 이다.

## 5. 단위 통일 규칙

### 5.1 기준 단위를 고르는 원칙

품목군마다 기준 단위 하나(`base_unit`). 고르는 순서:

1. **사장님이 발주 수량을 세는 단위**(재료 기준 단위, 결정 #42 와 같은 뜻). 계란은 개, 우유는 ml, 대파는 g.
2. 1 이 애매하면 **데이터셋에서 그 품목이 가장 많이 팔리는 단위**(6절 조사표).
3. 액체는 ml, 고체는 g, 낱개로 세는 것만 개.

### 5.2 다른 단위로 적힌 상품을 바꾸는 법

| 상품 단위 → 기준 단위 | 환산 | 환산값 없으면 |
|---|---|---|
| 개 → g (오이 2입, 양배추 1통) | `qty × ea_weight_g` | 비교에서 뺀다. "다른 단위로만 있음"으로 따로 보여 준다(지금 `otherUnits` 와 같음) |
| g → 개 (계란 1.8kg) | `qty ÷ ea_weight_g` | 위와 같음 |
| ml ↔ g (간장 1.9kg, 요거트 750ml) | `× density` · `÷ density` | 위와 같음 |

환산값은 **정해진 규격이 있거나 편차가 작을 때만** 적는다. 계란 60g(특란 규격), 슬라이스 치즈 18g, 라면사리 110g, 밀도(간장 1.2 · 식용유 0.92 · 우유 1.03 · 꿀 1.42 …)는 적고, 두부 1모(300~420g) · 대파 1단(0.7~1.5kg) · 김 1장(종류마다 다름)은 **비워 둔다**. 비워 둔 것은 근사값으로 채우지 않는다 — 틀린 최저가가 빈 칸보다 나쁘다. 오이 · 애호박 · 무 · 양배추 · 브로콜리 · 파프리카 · 아보카도 · 레몬 · 양상추는 근사값(`note` 에 "근사")으로 적었고, 추이에서 튀면 비운다.

### 5.3 수량을 어디서 읽나 (우선순위)

1. 크롤러가 규격에서 읽은 총량 · 단위(`total_qty` · `unit`, 결정적 파서 `units.py`, 약 75% 성공)
2. 없으면 LLM 라벨의 `qty` · `qty_unit`(상품명에서 읽음) — 해석 실패 25% 를 메운다
3. **교차 검증**: 기준 단위가 개인 품목군에서 1 의 g 값과 2 의 개수가 함께 있고 `g ÷ ea_weight_g` 가 개수의 절반 이하 · 두 배 이상이면 파서가 틀린 것으로 보고 **개수를 쓴다**(10/31 데이터셋 "지킴이계란 대란 1560g(30개입)" 이 46,800g 으로 읽힌 사례)
4. 둘 다 없으면 단위가격 없음 → 비교에서 뺀다

### 5.4 단위가격 표기

원 / 기준 단위 1(원/g · 원/ml · 원/개, 소수 넷째 자리) — API 는 결정 #57 과 같다. 데이터셋의 `단위가격_100`(원/100g)은 적재할 때 기준 단위로 바꾼다.

## 7. 집계 규칙

### 7.1 플랫폼별 최저가 (발주 화면)

```
대상   = 라벨.item_group_code = <품목군> AND form IN (RAW, PREPARED) AND 기준 단위 양 > 0
이상치 = 같은 품목군 · 같은 수집일 후보가 3개 이상일 때 단위가격 중앙값의 5배 밖 (지금 규칙 그대로)
점포   = 같은 사이트 · 같은 상품번호는 가장 싼 점포 하나 (식자재왕몰 점포 10곳)
결과   = 사이트마다 단위가격이 가장 낮은 상품 1개(+ 상위 3개), 사이트는 1위 단가 순
배달   = 가게 시군구로 배달 안 하는 사이트 · 점포 제외 (ADR-0011 그대로)
```

### 7.2 일별 추이 (시세 그래프)

```
점 하나 = (품목군, 사이트, 수집일) 의 최저 단위가격  — 7.1 과 같은 대상 · 이상치 규칙을 날짜마다 적용
기간    = 최근 N일(기본 30일), 그날 수집이 없는 사이트는 점이 없다(0 으로 채우지 않는다)
```

같은 날 같은 사이트에 수집이 두 번이면 나중 것. 사이트마다 1위 **상품**이 날마다 바뀌어도 된다 — 선은 "그 사이트에서 그 품목을 가장 싸게 살 수 있는 값"이다.

### 7.3 포함 · 제외 요약

| | 포함 | 제외 |
|---|---|---|
| 형태 | RAW · PREPARED | PROCESSED · NONFOOD · UNKNOWN |
| 단위 | 기준 단위 또는 환산 가능 | 환산값 없는 다른 단위(따로 표시) |
| 값 | 중앙값 1/5 ~ 5배 | 그 밖(이상치 건수로 보고) |
| 품목군 | `comparable = Y` | 부모(돼지고기 · 소고기 · 닭고기 · 치즈) |

## 8. 재료 → 품목군 매핑

사장님 재료(`ingredient.name`)는 자유 글자다. 품목군을 찾는 순서:

1. 재료 이름이 품목군의 이름 · 별칭과 **정확히 같다**(공백 · 대소문자 무시) → 그 품목군. `Taxonomy.group_for_name`
2. 별칭이 두 품목군에 있으면(등심) 매핑하지 않는다
3. 매핑 없음 → 지금처럼 **이름 검색 + 규칙 판정**(`ItemMatcher`)으로 답한다. 응답에 `itemGroup: null` 을 적어 화면이 "품목군 없음"을 알게 한다
4. 부모 품목군에 매핑되면(돼지고기) 최저가 한 줄이 아니라 **부위 품목군 목록**을 준다. 재료표에 부위 별칭이 있으면(돼지고기 = 앞다리살 · 목살) 그 부위로

재료에 품목군을 직접 저장하는 칸(`ingredient.market_item_group_code`)은 두지 않는다. 이름 매핑이 틀리는 재료가 보이면 그때 사장님이 고르는 칸을 더한다.

## 9. 분류 배치 (지라 229)

| 항목 | 내용 |
|---|---|
| 언제 | **시세 CSV 가 `market_product` 에 들어간 직후, 같은 실행 안에서**(백엔드 Spring Batch `marketProductLabelJob`, 적재 이벤트로 기동 — [ADR-0014](../adr/ADR-0014-market-label-spring-batch.md)). 크롤링과는 분리 — 배치는 사이트에 요청하지 않는다. 아래 Python 스크립트 설명은 실험용(시험지 · 프롬프트 비교)에 해당한다 |
| 입력 | Parquet 의 **고유 상품명**(10/31 판 395,000개) 중 품목군 별칭이 낱말로 든 것(후보). 후보가 아니면 LLM 에 보내지 않고 **라벨도 남기지 않는다** — 라벨 없음은 10절의 규칙 폴백으로 처리된다(비식품 · 표 밖 식품을 굳이 저장하지 않는다). 예외: 시험지 라벨링 `label_names.py` 는 받은 CSV 의 상품명을 거르지 않고 전부 보낸다(시험지 줄은 이미 후보로 만든 것) |
| 한 번에 | 상품명 40개 + 품목군 표 전체(약 3,500 토큰)를 한 요청. `json_schema` 로 응답 형식을 강제. `temperature` 는 **모델이 받으면 0**(재현성), **받지 않는 모델(gpt-5 계열)은 보내지 않는다** — 모델 이름으로 가르지 않고 0 으로 보내 본 뒤 400 `temperature` 미지원이면 생략으로 바꾼다(`classify.gms_chat`). 운영에서 모델을 올려도 코드 수정 없음 |
| 증분 | 이미 라벨이 있는 상품명(같은 `label_version`)은 보내지 않는다. 매주 새 상품명 수천 개 |
| 비용 기록 | 운영 배치: 요청 수 · 다시 보낸 수 · 입력 · 출력 토큰 · 형태별 건수를 `BATCH_STEP_EXECUTION.EXIT_MESSAGE`(시작 · 끝 시각은 같은 줄)에 남긴다. 실험 스크립트: `labels_<날짜>.md` (229 완료 조건) |
| 출력 | 운영 배치: `market_product_label` 에 바로 upsert. 실험 스크립트: `ai/data/market/labels.parquet` (+ 서비스 적재용 CSV). 열 = 4절 라벨 + `product_name` |
| 모델 | 팀 GMS 키(OpenAI 호환). 모델 · 주소는 `GMS_BASE_URL` · `GMS_MODEL` · `GMS_KEY` 환경 변수 |
| 실패 | 하루 한도(429 PerDay)면 그 자리에서 멈추고 지금까지 결과를 저장. 다시 돌리면 이어서 |

프롬프트는 `ai/prompts/market/item_group.md`, 응답 스키마는 `item_group.schema.json`. 프롬프트 · 품목군 표가 바뀌면 `label_version` 을 올린다.

## 10. 라벨 우선순위 · 폴백

```
라벨 있음 (confidence ≥ 0.6)  → 라벨대로
라벨 있음 (confidence < 0.6)  → UNKNOWN. 비교에서 뺀다
라벨 없음 (새 상품명)          → 규칙 ItemMatcher.isExact(상품명, 품목군 이름) 로 임시 판정. 다음 배치에서 라벨이 붙는다
```

규칙 코드(`ItemMatcher` · 크롤러 `match.py`)는 지우지 않는다. 규칙과 라벨이 다른 상품은 표본 확인 후보다(11절).

## 12. 알려진 한계 · 다시 볼 시점

- 상품명만 보고 판정한다. 상품 페이지의 상세 설명 · 원재료 표시는 쓰지 않는다(수집 범위 밖)
- 근사 환산값(오이 · 애호박 · 무 …)은 ±30% 오차가 있다. 추이에서 튀면 비운다
- 품목군 표는 식당 핵심 재료 위주 182개(부모 4개 포함)다. 표에 없는 식품은 라벨이 `null` 이라 이름 검색으로만 찾는다
- 같은 상품명이 사이트마다 다른 물건일 가능성은 무시한다(라벨 키 = 상품명)
- LLM 라벨도 틀린다. 표본 95% 기준을 못 넘기면 프롬프트 · 표를 고치고 `label_version` 을 올려 다시 돌린다
- **다시 볼 시점**: 품목군이 300개를 넘어 한 요청에 다 못 넣게 되면 카테고리별로 나눠 보낸다. 사장님 재료 이름의 매핑 실패가 잦으면 재료에 품목군 선택 칸을 더한다
