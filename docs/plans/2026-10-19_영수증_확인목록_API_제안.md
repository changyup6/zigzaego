# 영수증 확인 목록 · 확정 API 제안 (구현됨 → [docs/API.md](../API.md) 8절)

기준일: 2026-10-19 · 지라 S15P31A308-113 (+ 112 확정 주소) · 상위 문서: [자동 세팅 · 사진 입고 · 예측 설계](2026-10-14_자동세팅_입고_예측_설계.md) 3.1 · 4.3 · 4.4절 · DECISIONS #26 · #41 · [영수증 업로드 API 제안](2026-10-19_영수증_업로드_API_제안.md)(!92)

**제안과 달라진 점** (코드 `purchasedoc/controller/ReceiptController` · `ReceiptConfirmService` 기준, 상세는 Swagger): 묶음 `id` 는 상품명 그대로가 아니라 **상품명 UTF-8 의 base64url(패딩 없음)** 이다. 줄이 전부 자동 확정된 영수증은 job 이 끝날 때 바로 CONFIRMED 가 되지 않고 `GET /receipts` 의 `readyDocs` 에 올라, **`POST /receipts/docs/confirm` `{docIds}`** 로 확정할 때 재고에 들어간다(사장님이 정해 PENDING 줄이 0 이 된 문서는 제안대로 서버가 CONFIRMED). 묶음 확정에서 날짜를 못 읽은 영수증의 줄은 건너뛰고 응답 `skippedLineIds` 로 알려 주며, 묶음 줄이 모두 그렇다면 409 `RECEIPT_DATE_UNKNOWN`. 오류 코드가 더 있다: 400 `RECEIPT_INGREDIENT_REQUIRED` · `RECEIPT_UNIT_INVALID` · `RECEIPT_PACK_CONFLICT`, 409 `RECEIPT_LINE_ALREADY_DECIDED`. `POST /receipts/lines/confirm` 응답은 board + `confirm`(확정 요약).

영수증을 읽은 뒤(111) 사장님이 "이 상품은 어느 재료인가"를 확인하는 화면이 입고 탭 확인 목록이다(FE 76 완료, 목 `frontend/src/lib/mock/receipts.ts`의 `matches` · `confirmMatch`). 112 가 줄 확정 서비스(`ReceiptConfirmService.confirm`)를 만들고 있고, 113 은 그 줄들을 **상품명 단위로 묶어** 보여 주고 묶음 하나를 한 번에 확정한다. 서비스는 만들고, **HTTP 주소는 이 문서로 BE · FE 컨펌을 받은 뒤** 붙인다(!92 와 같은 방식).

**리뷰 요청**: BE-1(BE · 주소 · 오류 코드), PM·FE(FE · 묶음 모양 · 자동 확정 기준). 4절 "정할 것" 에 답을 달아 주시면 API.md 에 옮긴다.

## 1. 주소

| Method | URL | 하는 일 | FE 목 함수 |
|---|---|---|---|
| GET | `/receipts` (!92) | 장 목록 `files` 에 **확인 목록 `matches` · 재료 선택지 `options`** 를 더해 돌려준다 | `getReceipts` · `pollReceipts` |
| POST | `/receipts/matches/{matchId}/confirm` | 묶음 하나 확정 → 같은 상품명 줄 전부에 적용 | `confirmMatch` |
| POST | `/receipts/lines/confirm` | 줄 단위 확정(112 서비스 그대로). 화면은 안 쓰고, 상세 화면 · 운영 보정용 | — |

지라 113 은 `GET /receipts/jobs/{id}/review` 로 적혀 있다. FE 는 입고 탭에서 `getReceipts` 한 번으로 장 목록과 확인 목록을 같이 그리므로(입고 탭 `page.tsx` 가 `getReceiving` · `getReceipts` 를 같이 부름), **job 별 주소 대신 `GET /receipts` 에 붙이는 쪽**을 제안한다. 여러 번 나눠 올린 영수증도 한 목록에 모인다(4절 1번).

## 2. 요청 · 응답

### GET /receipts 의 `matches` · `options`

```json
{
  "files": [ … !92 2절 … ],
  "matches": [
    { "id": "냉동 칵테일새우 1kg", "name": "냉동 칵테일새우 1kg", "receipts": 12, "lineIds": ["801", "…"],
      "guess": "37", "qty": 12, "unitNeeded": false, "basePerPack": 1000, "baseUnit": "G",
      "past": false, "needsReview": true, "reasons": ["LOW_CONFIDENCE"] },
    { "id": "키친타올 6롤", "name": "키친타올 6롤", "receipts": 1, "lineIds": ["812"],
      "guess": "", "qty": 1, "unitNeeded": true, "basePerPack": null, "baseUnit": null,
      "past": false, "needsReview": true, "reasons": ["UNMAPPED"] }
  ],
  "options": [ { "id": "37", "name": "칵테일 새우" }, … ]
}
```

- **묶음** = 아직 정해지지 않은(`purchase_doc_line.status = PENDING`) 줄을 상품명(앞뒤 공백 · 연속 공백 정리)으로 묶은 것. `receipts` = 그 상품명이 나온 장 수, `qty` = 포장 개수 합.
- `id` 는 정리한 상품명 그대로(문자열). 확정 주소에서 URL 인코딩해 쓴다. 새로 올린 영수증에 같은 상품명이 나오면 기존 묶음에 더해진다(목 `addToGroup` 과 같은 동작).
- `guess`: 재료 id(사전 매칭 · LLM 제안), 모르면 `""` → FE 셀렉트 기본이 '주기형 품목'(`CYCLE`, DECISIONS #26).
- `unitNeeded` · `basePerPack`: 포장 1개 = 기준 단위 몇인지 모르면 `unitNeeded: true` 로 FE 가 '1개 = N g' 를 묻는다.
- `past`: 묶음의 모든 줄이 PAST(재고 확인일 이전) 영수증이면 true — 재고에 안 더해진다(가격 이력에만).
- `reasons`(FE `ReviewReason`): `UNMAPPED`(재료 없음) · `LOW_CONFIDENCE`(LLM 제안 확신도 낮음) · `UNIT_UNSET`(단위 미확정). 판정은 112 의 `ReceiptReview.reasons` 를 그대로 쓴다.
- 이미 정해진 줄(CONFIRMED · IGNORED)은 목록에서 빠진다. 자동 확정 줄도 빠진다(아래 3절).

### POST /receipts/matches/{matchId}/confirm

```json
{ "choice": "37", "basePerPack": 1000 }
```

- `choice`: 재료 id · `"cycle"`(새 주기형 품목) · `"ignore"`(무시 — 봉투값 · 비식자재).
- `basePerPack`: `unitNeeded` 일 때 필수(FE `confirmMatch` 의 `unitG`). 아니면 생략.
- 서버: 그 묶음의 PENDING 줄 전부를 112 `ReceiptConfirmService.confirm` 에 한 번에 넘긴다(한 트랜잭션). 사전(`supplier_product`) 저장 · 주기형 재료 생성 · `price_history(DOC)` 는 112 규칙 그대로.
- 응답: `GET /receipts` 와 같은 모양 + `gain`(재고에 더해진 양, 기준 단위. PAST · 주기형 · 무시면 0) — 목 `confirmMatch` 의 `gain` 과 같다.

| 경우 | 응답 |
|---|---|
| 그 상품명 묶음이 없음(이미 다 정해짐 포함) | 404 `RECEIPT_MATCH_NOT_FOUND` |
| `choice` 가 다른 가게 · 없는 재료 | 404 `COMMON_NOT_FOUND` |
| 단위 미확정인데 `basePerPack` 없음 | 400 `RECEIPT_UNIT_REQUIRED` (112) |
| 묶음 안 줄 중 문서 날짜를 못 읽은 줄 | 그 줄만 남기고 나머지 확정, 응답 묶음에 남은 줄 표시(4절 4번) |

### POST /receipts/lines/confirm

`{ "lines": [ { "lineId": "801", "action": "INGREDIENT", "ingredientId": "37", "baseQtyPerPack": 1000 } ] }` — 112 계약의 `LineDecision` 그대로. 지라 112 본문의 `POST /receipts/confirm {lines}` 를 이 이름으로 둔다.

## 3. 자동 확정 · 문서 확정

- **자동 확정**(설계 4.4 "확신도가 높으면 자동 확정"): 상품명이 사전(`supplier_product`, 같은 거래처 · 같은 상품명)에 이미 있고 그 상품의 단위가 정해진 줄만. 읽기가 끝난 줄 중 이 조건이면 서버가 줄 status 를 CONFIRMED 로 둔다(112 서비스)(DECISIONS #41 "자동 확정 줄은 CONFIRMED"). LLM 제안은 확신도와 무관하게 사장님 확인(4절 2번).
- **문서 확정**: DECISIONS #41 은 문서가 `CONFIRMED` 여야 재고에 들어간다. 제안: 문서의 줄이 모두 정해지면(PENDING 0) **서버가 그 문서를 바로 CONFIRMED** 로 바꾼다. 줄이 전부 자동 확정된 문서는 job 이 끝날 때 바로 CONFIRMED. 따로 "문서 확인" 버튼은 두지 않는다(FE 목에도 없음, 4절 3번).

## 4. 정할 것

1. **주소** — 지라의 `GET /receipts/jobs/{id}/review` 대신 `GET /receipts` 에 `matches` 를 붙이고, 확정은 `POST /receipts/matches/{matchId}/confirm`. 괜찮나? (규리 · 태정)
2. **자동 확정 기준** — 사전에 있고 단위가 정해진 줄만(LLM 제안은 항상 확인). 너무 보수적이면 "LLM 확신도 0.9 이상" 도 넣을지. (태정)
3. **문서 확정** — 줄이 다 정해지면 서버가 문서를 자동 CONFIRMED(버튼 없음). 사장님이 장 단위로 한 번 더 보는 단계가 필요한가? (태정)
4. **날짜 못 읽은 장** — 그 장 줄은 확정 못 하고 목록에 남는다(재고 · 가격에 못 씀). 날짜를 사장님이 넣는 칸을 둘지, 그 장을 지우고 다시 올리게 할지. (태정)
