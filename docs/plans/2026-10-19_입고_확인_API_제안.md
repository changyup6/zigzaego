# 입고 확인 API 제안 (구현됨 → [docs/API.md](../API.md) 9절)

기준일: 2026-10-19 · 지라 S15P31A308-71 · 상위 문서: [3주 개발 계획](3주_개발_계획.md) 4.2 · 7절, [자동 세팅 · 사진 입고 · 예측 설계](2026-10-14_자동세팅_입고_예측_설계.md) 3.1 · 4.2 · 4.3절 · DECISIONS #8 · #27 · #41 · #42 · #55

**제안과 달라진 점** (코드 `receiving/` · `purchasedoc/service/ReceiptConfirmService` 기준, 상세는 Swagger): 3절의 포장 단위 제안은 버리고 결정 #42 대로 **기준 단위**로 주고받는다 — 요청 `{receivedQty, unitPrice, basePerPack?}`, 피드 `incoming` 은 `unit` · `qty` · `unitPrice`, `history` 는 `recommendedQty` · `finalQty` · `receivedQty`. 포장 크기를 모르는 상품인데 `basePerPack` 이 없으면 400 `RECEIVING_UNIT_REQUIRED`. 입고 예정은 보낸(`SENT`) 발주서의 줄만이다(DRAFT 제외, #63). 영수증으로 채우는 경로는 문서 전체가 한 발주서에 맞을 때만 `purchase_doc.purchase_order_id` 를 채우고, 아니면 줄 단위로 `purchase_doc_line.purchase_order_item_id` 에 잇는다(V15, S15P31A308-301). 자동 입고된 줄(`auto_received`, 예정일 ±3일)도 후보가 되어 영수증 값으로 덮는다(#84). 이 경로의 가격 이력은 영수증의 `DOC` 행으로 쓰고 `RECEIVE` 행은 쓰지 않는다.

입고 탭(FE 76 완료)은 목(`frontend/src/lib/mock/receiving.ts`)으로 돌고 있다. 3주 계획 7절에 주소 한 줄(`PATCH /purchase-orders/{id}/items/{itemId}/receive {receivedQty, unitPrice}`)만 있고 API.md 에는 없다. 구현 전에 **주소 · 응답 모양 · 단위**를 BE · FE 와 맞추려는 문서다.

**리뷰 요청**: BE-1(BE · 발주 70 과의 연결 · 오류 코드), PM·FE(FE · 피드 모양). 4절 "정할 것" 에 답을 달아 주시면 API.md 에 옮기고 구현한다.

## 1. 주소

| Method | URL | 하는 일 | FE 목 함수 |
|---|---|---|---|
| GET | `/receiving` | 입고 탭 한 화면치: 입고 예정 줄 · 최근 발주 · 첫 입고 여부 | `getReceiving` |
| PATCH | `/purchase-orders/{orderId}/items/{itemId}/receive` | 입고 예정 줄 하나를 받은 양 · 단가로 입고 확인 | `confirmReceiving` |

- 모두 로그인 필수, 내 가게 것만. 남의 가게 id · 숫자 아닌 id → 404 (기존 `ResourceIds.parse` 규칙).
- 입고 예정 줄은 발주 70(BE-1)이 만드는 `purchase_order_item` 이다. **70 이 develop 에 들어오기 전에는 확인할 줄이 없다** — 71 은 70 뒤에 머지한다.

## 2. 요청 · 응답

### GET /receiving

```json
{
  "incoming": [
    { "orderId": "31", "itemId": "77", "ingredientId": "12", "name": "토마토 캔",
      "supplier": "OO상회", "packLabel": "3 kg 캔", "baseUnit": "kg", "basePerPack": 3,
      "orderedPacks": 4, "unitPricePerPack": 11700, "expectedDate": "2026-10-20", "today": false }
  ],
  "history": [
    { "orderId": "30", "itemId": "70", "date": "2026-10-16", "name": "생크림 1L",
      "recommendedPacks": 6, "finalPacks": 5, "supplier": "OO상회",
      "status": "RECEIVED", "receivedPacks": 5, "receivedAt": "2026-10-18T09:10:00+09:00" }
  ],
  "firstReceiptDone": true
}
```

- 입고 예정 = 취소 안 된(`cancelled_at` 없음) · 발주서 CANCELLED 아님 · 아직 입고 확인 안 된 줄 (V1 COMMENT 와 같은 정의).
- `history.status`: `DRAFT`(전송 대기) · `SENT`(보냄 · 입고 예정) · `RECEIVED`(입고 완료) · `CANCELLED`(거절). FE 목의 한글 상태 글자 · "10/4(토)" 날짜 표시는 FE 가 만든다(API.md 날짜 규칙: `YYYY-MM-DD` · ISO-8601).
- 최근 발주는 최근 14일, 최대 50줄(제안 — 4절 3번).
- 목의 `ingredients`(재고 · 8주 단가)는 넣지 않는다. 재고는 기존 재고 · 재료 조회를 다시 부르면 된다(입고 확인 응답 뒤 FE 가 이미 다시 부름).

### PATCH /purchase-orders/{orderId}/items/{itemId}/receive

```json
{ "receivedPacks": 4, "unitPricePerPack": 11700 }
```

| 경우 | 응답 |
|---|---|
| 정상 | 200 + `GET /receiving` 과 같은 모양(FE 목처럼 바뀐 피드 전체) |
| `receivedPacks` ≤ 0 · 소수 넷째 자리 이상 | 400 `COMMON_INVALID_INPUT` (DECISIONS #42) |
| `unitPricePerPack` 음수 · 소수 | 400 `COMMON_INVALID_INPUT` (DECISIONS #55, 원 정수). 0 · 생략 = 거래처 상품 단가 그대로 |
| 이미 입고 확인된 줄 | 409 `RECEIVING_ALREADY_RECEIVED` |
| 취소된 줄 · 취소된 발주서 | 409 `RECEIVING_CANCELLED` |
| 남의 가게 · 없는 id | 404 |

**서버에서 일어나는 일** (한 트랜잭션):
1. `purchase_order_item.received_qty` = `receivedPacks`, `received_unit_price` = `unitPricePerPack`, `received_at` = 지금.
2. 재고: 따로 쓰지 않는다. 추정 재고가 `received_qty × base_qty_per_pack` 를 이미 더한다(`InventoryEstimateService`, DECISIONS #41 ①).
3. `price_history` 에 `source=RECEIVE` 1행(포장 1개 단가, 기존 `SupplierProductService` 의 MANUAL 기록과 같은 단위 규칙). 단가를 안 바꿨으면 그래도 1행(실제로 산 값이라 가격 지수 이력이 됨).
4. 그 재료의 첫 입고면 `ingredient.unit_status = LOCKED` (설계 3.1절).

### 영수증으로 채우는 경로 (주소 없음)

영수증 줄 확정(112)이 같은 입고 예정 줄을 찾으면 **위 2~4번을 같은 서비스 메서드로** 부르고, 그 영수증의 `purchase_doc.purchase_order_id` 를 채운다(연결된 문서 줄은 재고에 이중으로 더하지 않음 — DECISIONS #41). 주소는 추가하지 않는다.

## 3. 단위 — 이번 제안의 핵심

FE 목은 받은 양 · 단가를 **기준 단위(kg · 원/kg)** 로 보낸다(`IncomingLine.qty` 12 kg, `unitPrice` 3900). DB 는 `received_qty` 를 **포장 개수**로 읽고(재고 계산이 `base_qty_per_pack` 을 곱함), 단가도 **포장 1개 값**이다(`price_history` · `supplier_product.price`).

제안: **API 는 포장 단위로 주고받는다**(`receivedPacks` · `unitPricePerPack`). 응답에 `basePerPack` · `baseUnit` · `packLabel` 을 같이 주니 FE 가 "12 kg (3 kg 캔 4개)" 처럼 보여 줄 수 있다.
- 이유: 사장님은 "캔 4개 왔다" 로 확인한다. 서버가 kg → 포장 수로 나누면 `base_qty_per_pack` 이 빈 상품에서 깨진다(첫 입고 전에는 비어 있을 수 있음, 설계 3절).
- `base_qty_per_pack` 이 빈 상품은 `basePerPack: null` — FE 는 포장 수만 보여 준다.

## 4. 정할 것

1. **단위** — 위 3절대로 포장 단위로 주고받나? (태정 · 규리) 기준 단위로 가면 FE 는 그대로, 대신 서버가 나눗셈 · 빈 `base_qty_per_pack` 처리를 정해야 한다.
2. **주소** — `GET /receiving` 한 화면치 + 3주 계획의 `PATCH …/receive` 그대로. 70 의 발주서 주소(`/purchase-orders`)와 겹치는 데 없나? (규리)
3. **최근 발주 범위** — 14일 · 50줄이면 되나? (태정)
4. **고쳐 입력** — 입고 확인을 잘못 눌렀을 때 409 로 막고 고치기는 다음 일감으로 미룰지, 지금 같은 주소로 덮어쓰기를 허용할지. 덮어쓰면 `price_history` 줄도 고쳐야 한다. (규리 · 태정)

## 5. 이 문서에서 다루지 않는 것

- 발주서 만들기 · 메시지 · 승인(69 · 70) — 71 은 그 결과 줄을 받기만 한다
- 영수증 줄 매칭 · 확정(112), 확인 목록(113)
- 실사 · 재고 직접 고치기(`stock_count`)
