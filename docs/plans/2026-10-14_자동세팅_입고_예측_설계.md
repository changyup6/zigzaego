## 0. 목표와 일정

- **목표**: 사장님 입력 없이 재고가 돌아가게 한다. 레시피는 메뉴 정보로 자동 세팅하고, 입고는 영수증 사진으로 채운다.
- **개발 3주**: 10/12(월) ~ 11/01(일). 10/05 ~ 10/11은 기획 주간이라 포함하지 않는다.
- **11/02부터 실사용**하며 수정. 최종 발표는 11월 말.
- **11/02까지 필수**: 아래 전부. **실사용 기간으로 미루는 것**: 백테스팅 비교표 하나.
- 늦어질 때의 대체 경로는 각 절에 적어 두었다. 범위를 줄이는 장치가 아니라 실사용 첫날이 멈추지 않게 하는 장치다.

## 1. 전체 구조

> **ai-batch(TimesFM 야간 예측)는 #91 로 서비스 예측에서 뺀다 ([DECISIONS #91](../DECISIONS.md), 5.2절).** 스테이징 배치 내리기는 S15P31A308-312. 아래 그림과 표의 TimesFM 은 #91 전 구조다.

```
[사장님 폰 · PC]  React (화면 5개 + 로그인)
      │  REST (store 스코프 강제)
      ▼
[EC2 1대 · Docker Compose]
 ├ spring     API 서버. 비동기 작업(@Async)도 여기서 실행
 │   ├─▶ Apify      네이버 플레이스 · 요기요 메뉴 수집 (온보딩)
 │   ├─▶ GMS        LLM: 메뉴 구성 추출 · 정규화 · 영수증 정형화 · 품목 매칭
 │   └─▶ CLOVA OCR  General OCR + 표 추출 (영수증)
 ├ postgres
 ├ ai-batch   Python. cron 03:00 TimesFM 예측 → forecast 테이블
 └ /data      볼륨. 영수증 · 레시피 파일 · 메뉴판 이미지
```

| 원칙 | 내용 |
|---|---|
| API 서버는 Spring 하나 | 외부 서비스는 전부 Spring이 HTTP로 호출 |
| Python은 배치만 | Spring과 서로 호출하지 않는다. DB 테이블로만 주고받는다 |
| 오래 걸리는 작업은 비동기 | 온보딩 · 영수증 모두 `job` 테이블 + 화면 2초 폴링 |
| 대체 경로 | TimesFM 없음 → 요일 평균. 통계식 데이터 부족 → 기존 식(7일 평균 × N) |
| 멀티테넌트 | 모든 신규 테이블에 store_id ([ADR-0002](../adr/ADR-0002-multi-tenant-store-scope.md)) |

### 1.1 외부 서비스

| 서비스 | 용도 | 비용 (2026-10-14 확인) |
|---|---|---|
| Apify `zen-studio/naver-place-scraper` | 네이버 메뉴명 · 가격 · 설명 · 사진 URL | 가게 1곳 약 $0.01. Free 플랜 월 $5 크레딧 |
| 요기요 웹 | 메뉴 전체 · 설명 · 사진 URL | — |
| GMS | LLM (멀티모달 포함) | SSAFY 제공 |
| CLOVA OCR General | 글자 3원 + 표 22원 = 건당 25원. 매월 무료 100건 | 기본료 없음 |

- CLOVA 영수증 전용 모델(Document OCR, 월 18,000원 고정)은 **보류**. 1주차 비교에서 General + LLM이 영수증에서 기준 미달일 때만 신청한다. 신청하면 종료 시 해지한다.
- Apify 이용약관상 수집 데이터의 적법성 책임은 사용자에게 있다(제5.8조 · 제11.1조). 수집 대상과 방식으로 리스크를 판단한다.

## 2. 온보딩

### 2.1 단계

| 단계 | 필수 | 건너뛰면 |
|---|---|---|
| ① 가게 찾기: 상호명 → Apify 네이버 검색 → 후보 카드에서 탭. 링크 입력은 선택 | **필수** | — |
| ② 메뉴 수집: Apify 네이버. 요기요에서 같은 가게가 찾아지면 동의 1회 후 함께 수집 | **필수** | — |
| ③ 레시피 확인: 질문 답하기 / 레시피 파일 올리기 / 건너뛰기 | 선택 | LLM 추정값으로 시작. 확인 필요로 표시 |
| ④ 홈 설정 체크리스트: POS 연결 · 거래처 · 첫 입고 · 재고 실사 | 선택 | 체크리스트에 남음. 다 채우면 사라짐 |

- POS를 건너뛰면 수집한 메뉴가 메뉴 목록의 기준이다. 나중에 POS 엑셀을 올리면 기존 메뉴명 연결 화면에서 연결하고, 포스에만 있는 메뉴는 그때 추가한다.

### 2.2 수집 실패와 메뉴 0개

| 상황 | 처리 |
|---|---|
| Apify 일시 실패 (액터 오류 · 프록시 · 시간 초과) | 자동 재시도 2회 (30초 · 2분 간격) → 실패 시 "다시 시도" 버튼 |
| 네이버 메뉴 0개 | 요기요 메뉴로 진행 |
| 네이버 · 요기요 모두 메뉴 0개 | **메뉴판 사진 올리기 단계가 나타난다** |
| 메뉴가 일부만 있음 | 그대로 진행. 메뉴 화면에서 "메뉴판 사진으로 추가"는 선택 기능 |
| 요기요만 실패 | 네이버 결과로 진행 |

### 2.3 수집 소스 규칙

| 소스 | 판정 |
|---|---|
| 네이버 플레이스 (Apify) | 사용. 메뉴명 · 가격 · 설명 · 메뉴 사진 URL |
| 요기요 웹 | **사장님 동의를 받은 그 가게만**, 브라우저로 사람 속도로 읽는다. 요기요 약관 제21조 다목(영리 목적 정보 수집 금지)에 걸릴 소지가 있어 서비스화 전 제휴 문의 또는 법률 검토 |
| 쿠팡이츠 (Apify) | 제외. 앱 내부 API 사용 추정 |
| 배민 | 제외. 공개 웹 메뉴 페이지 없음 |
| 사장님 화면 녹화 | 제외 |
| 블로그 · 리뷰 글 · 리뷰 사진 | 제외. 네이버 검색 API 약관(2026-09-07) AI 입력 금지, 작성자 저작권 · 개인정보 |

- 외부 메뉴 사진은 **저장하지 않는다.** URL로 LLM에 넘기고 분석 결과 텍스트만 남긴다.
- 네이버 · 요기요 메뉴는 이름으로 병합한다. 요기요는 배달가라 가격을 매칭 기준으로 쓰지 않는다 (위글리 실측: 메뉴당 약 2,000원 차이).

### 2.4 분석 job

| 단계 | 처리 | 진척도 |
|---|---|---|
| 수집 | Apify 동기 호출 (최대 5분) | 0 → 30% |
| 정규화 | 중복 메뉴 합치기, 표기 통일 (불고기 = 소불고기), 소스 병합 | 30 → 35% |
| 구성 추출 | LLM **묶음 호출** (메뉴 약 10개씩). 사진이 있는 메뉴는 모두 포함, 묶음당 원본 합 10MB 까지 | 35 → 90% |
| 분류 · 초기값 | 재료별 종류(BOM / 1:1), 기준 단위, 보관 방식, 1인분 초기값과 확신도 | 90 → 95% |
| 질문 생성 | 확신이 낮은 **구성요소**만 객관식 | 95 → 100% |

- 구성 추출 결과는 **구성요소 BOM + 조합 규칙**이다. 위글리 예: 파스타볼 = 소스 6종 × 단백질 3종 + 토핑 세트, 더블 = 단백질 × 2, 세트 = 파스타볼 + 사이드 + 음료. 메뉴별로 적으면 약 170개 값이 필요한 것을 질문 6개로 줄인다.
- 메뉴 · 재료 · 레시피 행은 사장님이 ③을 끝내거나 건너뛸 때 저장한다. 그 전까지는 `job.result_json`에만 둔다. 저장한 추정값은 `recipe.source='AI'`, 다시 시도 · 메뉴판 사진은 새 job ([결정 #56](../DECISIONS.md)).
- 조합 규칙은 저장할 때 recipe 행으로 펼친다. 구성요소 g를 고치면 그 재료의 recipe 행을 같은 비율로 일괄 수정한다.
- 주기형 품목은 온보딩에서 만들지 않는다 (4.1).

### 2.5 분석 화면

- 메뉴 카드가 하나씩 넘어가며 진행 바가 찬다. 서버는 **전체 진척도 하나**만 계산하고(단계 전환은 실제 이벤트, 단계 안은 평균 소요 시간으로 보간), 화면이 그 값을 **메뉴 개수로 나눠** 메뉴마다 바를 채운다.
- 진행 바는 연출이고, 재료 구성 결과는 **묶음 호출이 실제로 끝났을 때** 한꺼번에 채운다.
- 화면을 나가도 job은 계속된다. 돌아오면 홈 체크리스트에서 이어진다.
- 예상 소요 2~5분 (미측정. 1주차 실측). 웹 푸시는 하지 않는다 (iOS는 홈 화면 설치 PWA만 지원, 알림은 기존 계획대로 실사용 이후). → 마감 재고 확인 알림만 웹 푸시로 보낸다 (DECISIONS #88).

### 2.6 레시피 확인

- 질문 예 (위글리): 파스타 면 1인분 / 로스트 치킨 · 불고기 · 새우 1인분 / 더블 미트러버의 소스 베이스 / 까르보나라 베이컨 여부.
- 레시피 파일(엑셀 · 문서 · 사진)을 올리면 LLM이 같은 구성요소 형식으로 변환하고, 파일에 있는 구성요소는 질문을 건너뛴다.
- 질문 · 확정 · 건너뛰기 · 1인분 수정 API 는 FE 목 모양 그대로(1인분 수정만 `PATCH /ingredients/{id}/serving`), 단위 표기 `g | ml | 개` ([결정 #56](../DECISIONS.md) · [API.md 6절](../API.md)).
- **소스 레시피는 받지 않는다.** 소스 원재료는 주기형으로 관리한다 (4.1).

## 3. 단위

| 분류 | DB 기준 단위 | 화면 표시 |
|---|---|---|
| 셀 수 있는 것 | 개 | 개 |
| 액체 | ml | 1,000ml 이상이면 L |
| 나머지 | g | 1,000g 이상이면 kg |

- 애매하면 **1인분을 무엇으로 세는가**로 정한다 (새우 5마리 → 개, 새우 60g → g, 고추장 → g).
- DB의 재고 · 레시피 · 소비량은 전부 기준 단위. 입고 확인과 발주 메시지는 포장 단위로 보여 준다.
- 포장 변환은 `supplier_product.base_qty_per_pack` (1단 → 1000). kg→g, L→ml 같은 표준 변환은 서버 고정 표.

### 3.1 단위 상태

| 상태 | 뜻 | 변경 |
|---|---|---|
| ESTIMATED | LLM 추정 | 자유 |
| CONFIRMED | 사장님이 질문에 답한 단위 | 첫 입고 전까지 자유 |
| LOCKED | 그 단위로 입고 기록이 생김 | 불가 |

- 질문을 건너뛴 재료는 **첫 입고 확인 화면에서 단위를 한 줄로 확인**한 뒤 LOCKED가 된다. 추정 단위가 사람 확인 없이 굳지 않는다.
- 비표준 포장(단 · 망 · 팩 → 개)은 첫 입고 때 LLM이 제안하고 사장님이 한 번 확인한다.
- 보조 단위(같은 재료를 개와 g로 함께 쓰기)와 단위 환산 기능은 **만들지 않는다.** 필요한 가게가 나오면 ingredient에 컬럼 두 개를 덧붙인다. 예외는 마감 재고 확인 입력 하나다. 사장님이 포장 단위로 말한 양을 `base_qty_per_pack`으로 기준 단위로 바꿔 저장한다 (DECISIONS #88).

## 4. 입고 · 영수증

### 4.1 품목 분류

| 분류 | 판정 | 차감 |
|---|---|---|
| BOM | 1인분을 바로 답할 수 있다 | 메뉴 판매 × 1인분 |
| 1:1 | 사 온 그대로 판다 (음료 · 주류 · 피타브레드) | 판매 개수 |
| 주기형 | 소스 원재료 · 양이 일정하지 않은 것 · 비식품 | 입고 기록으로만 (5.1) |

- **주기형은 영수증으로만 생성한다.** 영수증 품목 중 BOM · 1:1 어디에도 매칭되지 않으면 자동으로 주기형이 된다. 입고 기록 0개 = 품목 없음.
- 주기형은 **메뉴별 판매와 연결하지 않는다.** 메뉴별 계수를 계산하지도 저장하지도 않는다 (소스 레시피 역산 방지).
- 주기형 → BOM 이동은 사장님이 직접 할 때만.

### 4.2 처리 흐름 (job, 1장이든 50장이든 같은 경로)

```
업로드 (폰: 여러 장 선택 · 촬영 / PC: 끌어다 놓기, 이미지 · PDF)
 → /data에 원본 저장, receipt 행
 → 장마다 순서대로 (CLOVA 권장 1 tps)
     CLOVA General OCR(표 추출) → LLM 정형화 (품목명 · 수량 · 단위 · 단가 · 거래처 · 날짜)
     → receipt_line마다 매칭
         supplier_product에 같은 상품명 → 즉시 매칭 (LLM 없음)
         없음 → LLM이 재료 + 포장 변환 + 확신도 제안
                 BOM · 1:1 매칭 → 확인 목록
                 매칭 없음 → 새 주기형 후보
 → 날짜로 분류: 재고 실사일 이전 = PAST / 이후 = RECEIVE
```

- `supplier_product`는 처음에 비어 있다. 사장님이 확인한 매칭이 쌓여 상품명 → 재료 사전이 된다.
- 기존 승인 → 입고 예정 → 입고 확인 탭 경로(결정 #8)는 유지한다. 영수증은 그 확인 화면의 수량 · 단가를 자동으로 채운다.

### 4.3 반영

| | RECEIVE | PAST |
|---|---|---|
| 재고 | + (기준 단위) | 반영 안 함 |
| price_history | 기록 | 기록 |
| 주기형 소진 속도 | 반영 | 반영 (첫날부터 "기록 쌓는 중"을 건너뜀) |
| 입고 예정 | 해당 줄을 입고 완료 | — |

### 4.4 화면 ("입고 및 이력" 안)

- 처리 현황: 전체 진행 바 + 장별 상태(대기 / 인식 중 / 완료 / 실패 ↻) + PAST · RECEIVE · 확인 필요 개수. 장별 상태는 실제 값이다.
- 확인 목록: **상품명 단위로 묶는다.** 한 번 확인하면 같은 상품이 나온 모든 영수증에 적용되고 사전에 저장된다. 사전에 있고 확신도가 높은 줄은 자동 확정.
- 단위 미확정 재료는 여기서 단위 확인 한 줄.
- 실패한 장은 그 줄에서 재시도 · 삭제. 나머지 장은 계속 처리.

### 4.5 이미지 저장

- 로컬 · 스테이징은 서버 디스크(`/data` 볼륨), 운영은 S3(결정 #73, ADR-0013). DB에는 상대 경로만 두고, S3 에서는 그 값이 객체 키다.

### 5.1 추정 재고

| 품목 | 계산 |
|---|---|
| BOM | 실사 기준점 + 입고 − Σ(메뉴 판매 × 1인분) (3주 계획 4.2절) |
| 1:1 | 실사 + 입고 − 판매 개수 |
| 주기형 | 아래 표 |

주기형 소진식:

| 입고 기록 | 처리 |
|---|---|
| 0개 | 품목 없음 |
| 1개 | 기록 쌓는 중 |
| 2개 이상 + 그 사이 판매 데이터 있음 | **판매량 정규화**: 입고량 ÷ 그 사이 전체 판매 그릇 수 = 그릇당 소비량. 남은 일수 = 마지막 입고량 ÷ (그릇당 소비량 × 일별 예측 판매 그릇 수) |
| 2개 이상 + 판매 데이터 빔 | 평균 입고 간격으로 대체 |

전제: 입고 시점에 재고가 거의 바닥이었다. 미리 쟁여 두는 품목은 오차가 크다.

손계산 예시 — 생크림(ML, 주기형), 기준일 10/10. 숫자는 백엔드 테스트 `backend/src/test/java/com/zigzaego/api/inventory/InventoryEstimateServiceTest.java` 의 `cycle_creamExample_runsOutOn1017` 과 같다. 한쪽을 바꾸면 다른 쪽도 바꾼다.

| 입력 | 값 |
|---|---|
| 판매 | 9/12 ~ 10/10 매일 40그릇 (까르보나라 25 + 로제 15 — 메뉴 구분 없이 전체 그릇 수만 쓴다) |
| 입고 ① | 10/01 과거(PAST) 영수증 2,800ml (1L 2팩 + 800ml). 재고엔 더하지 않지만 속도 계산엔 쓴다 (결정 #41) |
| 입고 ② | 10/08 입고 4,000ml (1L 4팩) |

```
그릇당 소비량  = 2,800 ÷ (10/01 ~ 10/07 7일 × 40 = 280그릇)    = 10ml
추정 재고      = 4,000 − 10 × (10/08 ~ 10/10 3일 × 40 = 120그릇) = 2,800ml
하루 예상 소비 = 일별 예측 그릇 수 40 × 10                       = 400ml
남은 일수      = 2,800 ÷ 400 = 7일 → 10/11 2,400 … 10/16 400 → 10/17 0  ⇒ 소진 10/17
```

같은 전체 그릇 수면 메뉴 구성이 달라도 결과가 같고, 메뉴별 계수는 어디에도 저장하지 않는다 (결정 #26).

음수는 0으로 보정하고 "실사 필요" (결정 #9).

### 5.2 예측

> **#91 로 변경됨 ([DECISIONS #91](../DECISIONS.md)).** TimesFM 야간 배치는 서비스 예측에서 뺀다(스테이징 배치 내리기는 S15P31A308-312). 발주 추천 수요 예측은 이 절의 대체 경로(최근 4주 같은 요일 평균, 휴무일 제외)를 쓴다. 매출 예측은 지하철 이용객 수 예측 모델로 만든다. 아래는 #91 전 설계다.

- ai-batch 컨테이너 (EC2 안, cron). CPU 추론. GPU 불필요.
- TimesFM zero-shot, 배달 · 홀 분리. 포스에 채널 구분이 없으면 한 계열.
- Spring은 오늘자 TimesFM 값이 있으면 쓰고, 없으면 요일 평균. 예측 실패가 추천을 멈추지 않는다.
- 위글리: 배달 1년 이상, 홀은 10월 초 개업. 홀 이력이 짧아 TimesFM이 실제로 필요하다.
- Infra 확인: EC2가 x86인지 ARM(t4g)인지. ARM이면 arm64 이미지. 메모리 16GB 기준 여유 있음 (실측 필요). 모델 가중치는 이미지 또는 볼륨에 캐시.

### 5.3 안전재고

```
SS = z × σ × √(R + L)
  σ  최근 하루 소비량 표준편차 (BOM은 판매 × 레시피로 계산한 일 소비량)
  R  발주 주기, L 리드타임
  z  냉동 · 상온 97% (1.88) / 냉장 95% (1.65) / 신선 90% (1.28)
```

- 소비 이력 28일 미만 또는 주기형 품목 → 기존 식(최근 7일 평균 × N일).
- 보관 방식과 유통기한 기본값은 온보딩 때 LLM이 재료명으로 채운다. 사장님은 거래처와 재료 화면에서 고친다.
- 신문팔이 모형(폐기 비용 vs 품절 비용)은 서비스에 넣지 않는다. 비용 값을 사장님께 물어야 하기 때문. 백테스팅 실험으로만.

### 5.4 발주

```
발주점    ROP = 리드타임 수요 + SS            리드타임 수요 = Σ 예측 소비(오늘+1 … 도착일), 휴무일 0
발주 여부  추정 재고 + 입고 예정 ≤ ROP, 목표 재고 > 0
목표 재고  S = 리드타임 수요 + 주기 수요 + SS   주기 수요 = Σ 예측 소비(도착일+1 … 다음 도착일)
발주량    S − 추정 재고 − 입고 예정
          → 포장 단위 올림 → MOQ 이상
          → 상한: 하루 소비 × (유통기한 − 1일) − 추정 재고 − 입고 예정, max_order_qty
L · R     도착일 = 주문일(마감 지났으면 내일) + lead_time_days 이후 첫 배송 요일, 다음 도착일 = 도착일 + order_cycle_days 이후 첫 배송 요일
          L = 오늘 → 도착일, R = 도착일 → 다음 도착일. 배송 요일 · 마감이 없으면 L · R 상수 (DECISIONS #89)
```

> 2026-11-04 (DECISIONS #89, S15P31A308-263): 하루 소비 × 일수에서 날짜별 합으로, 배송 요일 · 마감 반영, 상한에 입고 예정 차감. 가격 연동 R' 은 하루 단위로 올린다. `next_order_date` = 다음 도착일에 맞춰 주문할 날.

- 가격 연동(3주 계획 4.8절)은 그대로. R만 조정하고 SS · ROP는 불변.
- recommendation에 사용한 예측 모델과 안전재고 식을 남긴다.

- 단가는 재료 기본 단위(개 · ml · g)당 가격으로 저장해 포장 크기가 달라도 비교한다. 사용자에게 보이는 단위 환산 기능은 여전히 없다 (3절).

#### 5.5.1 수집 방법 (조사 S15P31A308-122, 2026-10-27 · DECISIONS #68)

2.3절과 같은 기준으로 판정했다: 공식 API → 허용된 수집 → 불가 순서로 보고, 약관 위반 소지가 있으면 쓰지 않는다.

| 곳 | 판정 | 근거 (2026-10-27 확인) |
|---|---|---|
| 쿠팡 | **불가.** 자동 수집도, 파트너스 API도 쓰지 않는다 | 이용약관 제12조 4호: "회사의 사전 승인 또는 협의 없이 로봇, 스파이더, 스크레이퍼 또는 기타 자동화된 수단을 이용하여 회사의 사이버몰에 액세스하는 것" 금지. 제35조 ②: 서비스로 얻은 정보의 영리 목적 이용 · 제3자 이용 금지. `robots.txt`는 `User-agent: *` 에 `Disallow: /`. 서버에서 보낸 요청은 봇 차단(Akamai)으로 403. 쿠팡 파트너스 오픈 API 약관 제5조: "API 서비스를 통해 제공된 해당 데이터를 복제, 저장 또는 전송할 수 없습니다" — 하루 1회 저장 자체가 위반이고, 파트너스는 제휴 마케팅(최종 승인에 누적 매출 조건) 용도라 목적도 다르다 |
| 식봄 (foodspring.co.kr, 마켓보로) | **조건부 허용된 수집.** 공식 API 없음. 비로그인 공개 검색 페이지를 사람 속도로 읽는다 | 마켓보로 사이트 · 앱에 개발자 API 안내 없음, `robots.txt`가 `/API/` 차단. 비회원에게도 상품명 · 규격 · 가격이 보이고, `robots.txt`는 검색엔진 봇(Googlebot · Yeti · Bingbot · Daum)에 `/search/all` · `/goods/detail/` 를 허용. 이용약관(2026-04-01 시행)에 자동 수집을 금지하는 조항은 없다. 단 제5조 회원은 사업자 전용, 제12조 "상거래로서의 상품판매 또는 구매 이외의 목적으로 서비스를 이용하는 행위" · "회사 서비스를 방해하거나 장애를 발생시킬 수 있는 모든 행위" 금지, 제28조 회원이 취득한 정보의 외부 사용 금지 — **로그인한 회원 계정으로는 수집하지 않는다** |

식봄 수집 조건 (하나라도 어기면 중단):

1. 로그인 없이 공개 검색 페이지(`/search/all?key=<검색어>`)만 읽는다. 회원 계정 · 앱 내부 API · `/API/` 경로는 쓰지 않는다.
2. 하루 1회, 가게의 핵심 재료(10~15개)마다 검색어 1개. 요청 사이 3초 이상, 식별 가능한 User-Agent(서비스명 · 연락처).
3. 저장하는 것은 상품명 · 판매자 · 규격 · 표시 가격 · 수집 시각뿐. 상품 사진 · 설명 · 리뷰는 저장하지 않는다 (2.3절 사진 규칙과 같음).
4. 비로그인 표시가는 쿠폰 전 가격이고 사업자 회원가와 다를 수 있다. 화면에 "식봄 표시가 기준"으로 적는다.
5. 서비스화 전에 마켓보로(info@foodspring.co.kr)에 제휴 · 데이터 제공 문의를 보낸다. 약관 위반은 아니지만 부정경쟁방지법 (파)목 · 데이터베이스제작자 권리의 잔여 위험이 있어 요기요(2.3절)와 같은 수준으로 법률 검토 대상이다.
6. AI 파트가 분석용으로 만든 식봄 크롤러(S15P31A308-161 · 174 · 175)는 1회 수집용이다. 상시 수집기는 위 조건으로 BE가 따로 만들고, 산출물 재사용 여부는 AI 파트와 확인한다.

쿠팡 쪽: 3주 범위에서는 **식봄만 보여준다** (2026-10-27 결정, S15P31A308-123 은 식봄만 구현). 쿠팡 현재 판매가는 어떤 방법으로도 보여주지 않는다. 후속 후보는 사장님이 쿠팡에서 실제로 산 가격 — 영수증 · 거래명세서 OCR(4.2절, S15P31A308-112 · 113)이 `price_history.source='DOC'` 로 남기는 값과 수동 입력(`MANUAL`)을 "쿠팡 최근 구매가 (날짜)"로 표시하는 것 — 이고, 티켓은 따로 판다.

#### 5.5.2 재료 ↔ 상품 매칭과 단가 환산

- 검색어 = 재료 이름(`ingredient.name`). 사장님이 재료 고치기(`PATCH /ingredients/{id}` 의 `priceSearchKeyword`)에서 바꿀 수 있다(`ingredient.price_search_keyword`, V3). 별칭(`ai/seed/ingredient_catalog.csv` `aliases`)으로 자동 보정하는 것은 후속.
- 검색 첫 화면 결과(비로그인 기본 지역 기준, 8건 안팎) 중 앞 10개에서 규격을 읽을 수 있는 상품만 쓴다. 식봄은 규격 칸("1kg / EA", "15KG / EA", "1kg*10팩 / 1박스")을 그대로 파싱한다: 숫자 × 단위(kg · g · l · ml · 개) × 묶음 수. 페이지가 `__NEXT_DATA__` 에 넣어 둔 상품 데이터(상품명 · 규격 · 판매 단위 · 판매자 · 표시가 · 상품 번호)만 읽고 화면 마크업은 보지 않는다.
- 단위 단가 = 표시 가격 ÷ 재료 기준 단위 수량. 재료 단위가 G면 g당, ML이면 ml당, EA면 개당. 규격을 못 읽으면 그 상품은 버린다 (추정하지 않는다).
- 최저가 = 같은 재료의 단위 단가 최소. 재료 1건 = `mall_price` 행 1건(최저 상품 1건 + 비교한 상품 수)이고 후보 전체는 저장하지 않는다. 배송비는 3주 범위에서 비교에 넣지 않고(`supplier.shipping_fee` 칸은 이번에 쓰지 않음) 화면에 "배송비 별도"로 적는다. 이 값은 가격 지수(`price_history`)에 넣지 않는다.
