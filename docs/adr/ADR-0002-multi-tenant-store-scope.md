# ADR-0002: 첫날부터 멀티 테넌트, 모든 조회에 store 스코프 강제

- 상태: 채택
- 영역: backend
- 결정 로그: [DECISIONS #11](../DECISIONS.md)
- 관련 이슈: 3주 계획 1절 · 5절 · 8절

## 맥락

3주 안에 보이는 가게는 위글리 1곳이다. 그러나 다른 가게 사장님이 들어와 자기 가게를 만들 수 있어야 한다는 것이 제품 방향이다.
테넌트 구분을 나중에 넣으면 모든 테이블 · 쿼리 · 화면을 다시 뜯는다. 지금 넣으면 테이블 하나와 조회 조건 하나다.

## 결정

- 계정(`account`) · 가게(`store`) · 계정-가게(`account_store`, N:N) 테이블을 첫 마이그레이션에 넣는다
- 가게에 속한 모든 테이블은 `store_id` 컬럼을 가진다 (재료 · 레시피 · 거래처 · 추천 · 발주 · 재고 · 가격 이력 · POS 업로드)
- **모든 조회 · 쓰기는 로그인한 계정의 `store_id`로 강제한다.** URL · 쿼리 · 바디로 `store_id`를 받지 않는다. 다른 가게의 리소스 id는 404
- 위글리 고유값(가게 이름 · 문구 · 마감 시각 · 재료명)을 코드에 하드코딩하지 않는다. 전부 데이터
- 통합 테스트에 가게 2개를 넣고, 가게 A 계정으로 가게 B의 id를 호출했을 때 404인지 확인한다
- unique 제약은 `store_id`를 포함한다: `recommendation (store_id, ingredient_id, run_date)`

## 버린 대안

| 대안 | 왜 안 골랐나 |
|---|---|
| 단일 테넌트로 시작, 4주차에 추가 | 모든 쿼리와 테이블을 다시 손댄다. 3주차 시연 뒤 리팩토링할 시간이 없다 |
| URL에 `/stores/{storeId}/...` | 클라이언트가 남의 id를 넣을 수 있다. 서버가 매번 소유권을 검사해야 하고 빠뜨리기 쉽다 |
| Row Level Security (DB 수준) | PostgreSQL RLS는 가능하지만 팀이 익숙하지 않다. 애플리케이션 스코프가 테스트하기 쉽다 |

## 결과

- **좋아지는 것**: 공개 가입 · 온보딩 위자드(4주차)가 테이블 변경 없이 붙는다. 테스트가 "가게 2개"로 격리를 증명한다
- **감수하는 것**: 모든 리포지토리 메서드에 `store_id` 조건이 들어간다. 빠뜨리면 데이터가 샌다. 리뷰에서 반드시 본다
- **다시 볼 시점**: 한 계정이 여러 가게를 동시에 보는 화면이 필요할 때 (3주 범위 밖)
