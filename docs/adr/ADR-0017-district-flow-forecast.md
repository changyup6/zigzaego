# ADR-0017: 이번 주 매출 예측은 로컬 PC 가 지하철 이용객 예측 모델로 만들어 DB 에 넣고, BE 는 읽기만 한다

- 상태: 채택
- 영역: ai · backend
- 결정 로그: [DECISIONS #97](../DECISIONS.md) (#91 ② ④ 의 구체화)
- 관련 이슈: S15P31A308-226 · S15P31A308-267
- 바꾸는 것: 없음 (새 표 `sales_forecast_week` V20 · 가게 좌표 `store.latitude` · `longitude` V21 · 새 API `GET /sales-forecast/this-week`)

## 맥락

- 홈 · 발주 탭의 "이번 주 매출 예측" 카드(265)는 목으로 그렸다. #91 이 근거를 지하철 이용객 수 예측 모델(226)로, 분석 문장을 LLM(267)으로 정했다.
- 그 모델(seoulevent v3)은 7일 뒤 서울 상권의 지하철 승하차 급증을 예측한다. 행사 일정 · 공휴일 · 작년 같은 시기 · 상권별 과거 반응 29개 특징, XGBoost 허들 모델 + 보정.
- 매일 실행에 수집 16분 · 데이터 만들기 8분 · 예측 6 ~ 18분, 메모리 최대 약 9GB 가 든다. 스테이징 노드(4GB)에 맞지 않고 원천 데이터(약 1.2GB)를 둘 저장소도 없다.

## 결정

- **실행 = 로컬 PC, 매일 06:00 (Windows 작업 스케줄러).** `ai/scripts/register_daily_task.ps1` 로 등록하면 `python -m weglee_ai.seoulevent.daily` 가 수집 → 데이터 만들기 → 저장 모델로 예측(학습 안 함) → DB 적재를 한다. 코드는 `ai/src/weglee_ai/seoulevent/` (README 에 "로컬 실행" 명시).
- **DB 적재 = SSH → DB 파드 psql.** 터널 · DB 비밀번호 없이 서버 ssh 키로 `kubectl exec <DB 파드> -- psql` 을 부른다(`ai/scripts/demo_attach.py` 와 같은 방식). 넣을 곳(스테이징 · 운영)마다 서버 주소 · 키 · 네임스페이스를 `ai/.env` 에 둔다.
- **모델 교체 = 모델 폴더만.** `SEOULEVENT_MODEL`(기본 `model-v3`)이 가리키는 저장 모델을 바꾼다. 예측표 열(날짜 · 상권 · 구 · 평소 인원 · 예상 인원 · 행사 · 모델 · 모델 근거 · 위도 · 경도 · 좌석)이 계약이고, 표 · API · 화면은 그대로다. 어떤 모델이 냈는지는 `sales_forecast_week.model` 에 남는다.
- **가게 → 상권 = 반경 1km, 없으면 구.** 가게 좌표가 있으면 반경 1km 상권만, 없거나 그 안에 상권이 없으면 `store.sigungu` 의 구 전체. 구 단위는 고척돔 행사 날 상권 3배가 구로구 전체 +1% 로 묽어진다(검증: 반경 1km 는 +13%). 서울 밖이면 줄을 만들지 않고 BE 는 `pct` null 로 답한다.
- **이유별 기여 = 늘어난 인원을 한 번만 나눈 것.** 상권 · 날의 늘어난 인원을 모델 근거(SHAP) 비율로 나눠 행사(+ 좌석 수)와 행사 밖 이유(작년 같은 시기 · 공휴일 · 벚꽃 철)로 모은다. 요일 · 달 · 상권 크기와 해당 없는 근거(공휴일 아닌 날의 '공휴일')는 이유로 쓰지 않는다. 날씨는 모델에 없어 쓰지 않는다.
- **설명 문장 = GMS.** 숫자 · 행사 · 모델 근거만 넘기고 지어내기 · 날씨 · "재료를 넣어 두었다" 류 문장을 금지한다(`ai/src/weglee_ai/sales_forecast/prompts/analysis.md`). 같은 상권 묶음은 한 번만 부르고, 숫자가 그대로면 지난 문장을 다시 쓴다. 실패하면 `analysis` null, 숫자는 그대로.
- **BE 는 읽기만.** `SalesForecastService` 는 이번 주 줄을 그대로 돌려주고 오늘에 `today` 표시만 붙인다.

## 버린 대안

| 대안 | 왜 안 골랐나 |
|---|---|
| 클러스터 CronJob(ai-batch) 매일 실행 | 데이터 만들기 9GB 가 노드(4GB)를 넘고, 원천 데이터를 둘 S3 · 수집 키 시크릿 등 인프라 일이 크다 |
| 로컬에서 kubectl port-forward / SSH 터널로 DB 직접 접속 | DB 비밀번호 · 포트 관리가 늘어난다. 팀에 이미 ssh → kubectl exec → psql 경로가 있다 |
| BE 가 예측 · LLM 호출 | 모델 · 특징이 Python 이고, 조회마다 계산하면 느리다. "같은 주 두 번째 호출은 LLM 을 다시 부르지 않는다"(267)를 표 저장으로 지킨다 |
| 구 단위만 | 가게 바로 앞 행사가 구 전체로 묽어진다. 좌표 없는 가게의 대체로만 쓴다 |

## 결과

- **좋아지는 것**: 카드가 실제 예측으로 바뀐다(FE 목 → API). 서버 자원 · 인프라 변경 없이 돈다. 모델을 바꿔도 BE · FE 를 고치지 않는다.
- **나빠지는 것 · 한계**: 로컬 PC 가 꺼져 있으면 갱신이 멈춘다(켜지면 놓친 실행 1회, 카드는 마지막 적재 값). 지하철 인원 배수를 매출 배수로 그대로 쓴다(탄력 1). 목표(정밀도 0.8 · 재현율 0.7) 미달 모델이다.
- **남은 일**: 가게 좌표 채우기(온보딩), 운영 DB 접속 정보(운영은 다른 서버 · 다른 키, ADR-0015), FE 목 교체.
