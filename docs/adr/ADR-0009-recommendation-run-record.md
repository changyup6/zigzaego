# ADR-0009: 추천 생성 실행 기록을 표로 남겨 같은 날 재실행은 계산을 건너뛴다

- 상태: 채택
- 영역: backend
- 결정 로그: [DECISIONS #59](../DECISIONS.md)
- 관련 이슈: S15P31A308-188

## 맥락

- 추천 생성(`POST /recommendations/run` · 04:00 배치)은 발주가 필요한 재료만 `recommendation` 에 남긴다. "오늘 계산을 끝냈다" 는 사실은 어디에도 남지 않는다.
- 그래서 같은 날 다시 실행하면 "발주 불필요" 재료를 전부 다시 계산한다. 부하 시험에서 두 번째 실행도 첫 실행과 같은 39쿼리 · 300ms 였다(지라 158 뒤).
- 사장님은 홈 화면을 열 때마다 run 을 부를 수 있고, 배치와 수동 실행이 같은 날 겹친다. 재고 추정 · 예측 · 소비량 조회가 매번 반복된다.
- `recommendation` 은 `(store_id, ingredient_id, run_date)` unique(ADR-0002 · 3주 계획 8절)라 재실행이 기존 건을 바꾸지는 않는다. 문제는 결과가 아니라 비용이다.

## 결정

- Flyway `V4__recommendation_run.sql` 에 가게 · 날짜별 실행 기록 표 `recommendation_run` 을 둔다:
  `store_id, run_date, started_at, finished_at, created_count, no_order_count`, `(store_id, run_date)` unique.
- `RecommendationService.run` 은 그날 **끝난**(`finished_at` 있는) 실행 기록이 있으면 재고 추정 · 예측 · 소비량을 조회하지 않고 기존 추천만 돌려준다.
  응답 `RecommendationRunResponse` 의 모양은 그대로 — 건너뛴 실행은 `createdCount` · `noOrderCount` 0, `existingCount` 는 그날 추천 수.
- 실사 · 입고 · 레시피가 바뀐 뒤 다시 계산하려면 `POST /recommendations/run?force=true` 로 명시한다. 그래도 기존 건은 두고(하루 한 재료 한 건) 없는 재료만 새로 계산한다.
- 기록은 계산과 같은 트랜잭션에서 `INSERT ... ON CONFLICT (store_id, run_date) DO UPDATE` 로 쓴다. 계산이 실패하면 기록도 남지 않아 다음 실행이 다시 계산한다.
- 모든 조회 · 쓰기는 `store_id` 조건을 건다(ADR-0002). 실행 기록을 보여 주는 API 는 두지 않는다.

## 버린 대안

| 대안 | 왜 안 골랐나 |
|---|---|
| "발주 불필요" 재료도 `recommendation` 에 0 수량으로 저장 | 추천 목록 · 승인 · 발주서 만들기가 전부 "0 건 거르기" 를 알아야 한다. 표의 뜻("사라고 한 것")이 흐려진다 |
| 서버 메모리 · Redis 에 "오늘 돌렸다" 플래그 | 파드가 재시작되면 사라져 다시 계산한다. 건수 · 시각 같은 운영 정보가 남지 않는다 |
| 재실행을 아예 막고 409 | 배치가 실패한 날 수동 실행으로 메우는 경로가 막힌다. 홈 화면이 run 을 부르는 지금 흐름도 깨진다 |
| 바뀐 데이터(실사 · 입고 · 레시피)를 감지해 자동 재계산 | 변경 시각을 표마다 추적해야 한다. 3주 안에는 사장님이 `force=true` 로 명시하는 쪽이 단순하다 |

## 결과

- **좋아지는 것**: 같은 날 두 번째 실행부터 추천 조회 수준의 쿼리만 보낸다. 가게 · 날짜별 실행 시각 · 건수가 남아 배치가 돌았는지 확인할 수 있다
- **감수하는 것**: 실행 뒤 재료 · 실사 · 입고가 바뀌어도 `force=true` 없이는 그날 다시 계산하지 않는다. 화면 · 배치가 이 규칙을 알아야 한다
- **다시 볼 시점**: 사장님이 실사 뒤 "왜 추천이 안 바뀌냐" 고 묻는 일이 잦아지면 변경 감지 자동 재계산으로. 주기형(CYCLE) 재료 추천이 들어오면 건너뛰기 조건을 다시 본다
