# ADR-0020: 시연 자료 commit 후 추천을 계산하고 준비 완료를 공개한다

- 상태: 채택
- 영역: backend · ai
- 관련 이슈: S15P31A308-343 · 344 · 347

## 맥락

온보딩 레시피 저장은 가게의 메뉴·재료·레시피가 저장됐다는 뜻이다. 시연용 판매 이력·재고·주문·고정 주 예측은
별도 운영자 프로세스가 복사한다. 그 전에 추천을 실행하면 정상적인 빈 결과가 당일 완료 캐시에 남아,
자료가 들어온 뒤에도 추천을 계산하지 않는다. 자료 복사와 추천 계산의 성공을 구분해야 한다.

## 결정

V22 `demo_preparation`은 `store_id`를 기본키로 갖는 가게별 준비 상태다.

| 상태 | 의미 | 쓰는 주체 |
|---|---|---|
| NOT_STARTED | 아직 요청하지 않음. 행이 없으면 조회에서만 이 값 | BE 조회 |
| PREPARING / ATTACH | 기본 레시피 저장 완료, 자료 복사 대기/진행 | BE 등록 → Python |
| DATA_READY / RECOMMENDATION | 이력·재고·주문·고정 주 예측이 모두 커밋됨 | Python |
| READY / RECOMMENDATION | 추천 실행과 그 완료 기록까지 커밋됨 | BE |
| FAILED | 실패한 `phase`, 안정적인 `error_code`, `retryable` 공개 | 해당 단계 실행기 |

- 대상은 `StoreClock.isDemoStore`가 판정하는 현재 설정된 시연 이메일 소속 가게뿐이다.
  재가입으로 이메일이 보관용으로 바뀐 옛 계정과 일반 계정은 대상에서 빠진다. 이름·이메일 상수는 두지 않는다.
- 기본 메뉴·재료·레시피가 실제 저장된 레시피 confirm/skip 트랜잭션에서 PREPARING을 등록한다.
  롤백하면 등록도 롤백한다. 중복 confirm은 기존 상태를 초기화하지 않는다.
- `GET /stores/me/demo-preparation`은 읽기만 한다. `POST .../retry`는 본문 없이 현재 가게만 처리한다.
  기본 레시피가 없으면 409, 일반 계정도 409. 진행 중/READY 재요청은 상태를 바꾸지 않는다.
- FAILED의 명시적 재시도는 행을 잠그고 `attempt`를 한 번 올린다. ATTACH 실패는 PREPARING으로,
  RECOMMENDATION 실패는 DATA_READY로 보낸다. 추천 실패 때문에 이미 복사한 이력을 다시 넣지 않는다.
- Python은 PREPARING 행을 잠근 뒤 사전 생성물을 복사한다. 이력과 고정 주 예측이 성공한 같은 트랜잭션에서
  DATA_READY를 쓴다. 실패 시 복사를 롤백한 뒤 같은 attempt에만 FAILED를 기록한다.
- BE는 DATA_READY를 `FOR UPDATE SKIP LOCKED`로 하나씩 잡는다. 현재 대상 가게·기본 레시피·그 가게 시계의
  이번 주 예측(7일)이 있는지 확인하고 추천을 계산한다. 추천과 실행 기록, READY는 같은 트랜잭션이다.
  실패하면 모두 롤백한 뒤 별도 트랜잭션에서 같은 attempt의 FAILED를 기록한다.
- 추천의 `force=true`로 이전 버전의 조기 빈 완료 캐시도 복구한다. 기존 추천·승인·거절은 유지하며
  `(store_id, ingredient_id, run_date)` 유일성으로 중복 추천을 막는다.
- 시연 가게가 DATA_READY/READY가 되기 전 `/recommendations/run`은 409로 막아 빈 완료 캐시를 남기지 않는다.
  일반 가게의 정상 빈 결과와 기존 추천 계약은 그대로다.
- 운영자 4프로필에서는 JobRecovery와 스케줄링 인프라를 등록하지 않는다. 자료 복사/저장본 러너가
  공유 DB의 실시간 사용자 작업이나 추천·입고·푸시 배치를 실행하지 않게 한다. 웹 재시작 복구는 유지한다.

## 대안과 결과

온보딩 job을 재사용하면 분석 성공과 이후 시연 자료 준비가 같은 상태에 섞이고, 일반 사용자의 재시도 의미까지
바뀐다. 기존 온보딩 job을 유지하고 작은 가게별 표로 후속 단계를 표현한다.

복사 프로세스의 `--forever` watcher는 PREPARING과 명시적 재시도를 처리하고, 웹 서버는 DATA_READY를 기본 1초마다
확인한다. 프로세스가 중단되면 상태가 READY로 바뀌지 않는다. 복사 트랜잭션이 커밋되지 않았으면 PREPARING에서
watcher를 다시 실행할 수 있고, DATA_READY면 웹 서버가 다음 조회 주기에 계산을 재개한다. 외부 API/예외/SQL 원문은
오류 응답에 넣지 않는다. 스키마와 운영자 복사기의 프로토콜 변경은 함께 배포해야 한다.
