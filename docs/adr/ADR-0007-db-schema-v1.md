# ADR-0007: DB 스키마 V1 — 22개 표, 단일 키, DB 와 서버의 검사 경계

- 상태: 채택
- 영역: backend
- 결정 로그: [DECISIONS #38](../DECISIONS.md) · [#40](../DECISIONS.md) · [#41](../DECISIONS.md)
- 관련 이슈: S15P31A308-32

## 맥락

3주 계획 5절은 표 15개를 적었다. 사장님 미팅(2026-10-07), 매입 문서 10종 실측, 2026-10-14 기획 변경과
설계(`docs/plans/2026-10-14_자동세팅_입고_예측_설계.md`) 7절을 반영하면서 매입 문서·문서 줄·포스 원본 줄·세트 구성·별칭·휴무일·job 이 더해져 22개가 됐다.
키 전략·타입·상태값 표현은 어느 문서에도 없어 스키마 작업 중 정해야 했다.
가게 단위 격리는 [ADR-0002](ADR-0002-multi-tenant-store-scope.md), Flyway·PostgreSQL 은 [ADR-0004](ADR-0004-backend-stack-baseline.md)가 정했다.

## 결정

- Flyway `V1__init_schema.sql` 하나에 22개 표를 FK 순서대로 만든다. 설명은 같은 파일의 `COMMENT ON` 이 정본이고, [erd.md](../design/erd.md)는 그림이다.
- PK 는 모든 표에서 `id BIGINT GENERATED BY DEFAULT AS IDENTITY` 단일 키. 중복 금지는 별도 unique 제약으로 건다.
- `store`·`account` 를 뺀 모든 표에 `store_id BIGINT NOT NULL REFERENCES store(id)`.
- 상태값은 `VARCHAR` + `CHECK (... IN (...))`. 금액은 `NUMERIC(12,2)`, 수량은 `NUMERIC(14,3)`.
- **DB 가 검사하는 것**: FK(가리키는 행이 있는지), `NOT NULL`, `CHECK`(값 목록·범위·자기 자신 참조 금지), unique.
- **서버가 검사하는 것**: 가게 간 FK 일치(1번 가게 행이 2번 가게 행을 가리키지 않는지), 상태 전이 순서(추천 `PENDING → APPROVED|REJECTED` 한 번 등),
  표를 넘는 일관성(세트 메뉴의 `kind='SET'`, 옵션 줄이 같은 영수증인지 등, erd.md "확인 필요" ⑥ 목록),
  입고 규칙(#41) 계산 — 문서 `CONFIRMED` · `kind='RECEIVE'` · 줄 재료 연결 · 줄 `status='CONFIRMED'` · 발주서와 안 묶인 줄만 더한다.
- 입고 규칙은 DECISIONS #41 과 SQL `COMMENT` 로만 적고 DB 뷰·함수로 만들지 않는다.

## 버린 대안

| 대안 | 왜 안 골랐나 |
|---|---|
| 복합 PK·복합 FK `(store_id, id)` | 가게 간 참조를 DB 가 막지만 모든 FK·JPA 매핑이 두 칸이 된다. 22개 표 전부에 퍼져 3주 안에 감당하기 어렵다 |
| PostgreSQL `ENUM` 타입 | 값을 더하거나 지우려면 타입 변경 마이그레이션이 필요하다. `CHECK` 는 제약만 바꾸면 된다 |
| 포스 판매를 하루 합계(`pos_sale`)만 저장 | 옵션 줄이 어느 메뉴에 붙었는지 사라져 되살릴 수 없다(#40). 원본 줄 `pos_sale_line` 을 함께 둔다 |
| 입고 계산을 DB 뷰·함수로 | 규칙이 아직 바뀌는 중이다(8차에 줄 상태 조건 추가). 서버 코드와 테스트로 고치는 쪽이 빠르다 |

## 결과

- **좋아지는 것**: 표마다 키·`store_id`·타입 규칙이 같아 JPA 엔티티를 같은 틀로 만든다. 값 목록을 마이그레이션 한 줄로 바꾼다.
  표·칸 설명이 DB 안에 있어 ERD 도구(ERDCloud)로 옮겨도 남는다
- **감수하는 것**: 가게 간 참조·상태 전이·입고 규칙을 DB 가 막지 않는다. 서버 코드와 두 가게 격리 테스트(S15P31A308-35)가 빠지면 잘못된 행이 들어간다
- **다시 볼 시점**: 격리 테스트에서 가게 간 참조 버그가 나오거나, erd.md "확인 필요" ②·⑥ 에서 일부를 복합 FK·`CHECK`·트리거로 옮기기로 정할 때.
  V1 이 한 번이라도 공유 DB 에 적용되면 그 뒤 변경은 V2 이후 파일로만 한다
