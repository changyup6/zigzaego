# ADR-0003: API 명세는 code-first Swagger

- 상태: 채택
- 영역: backend
- 결정 로그: [DECISIONS #19](../DECISIONS.md)
- 관련 이슈: 3주 계획 7절

## 맥락

BE 2명, FE 1명, 3주. 엔드포인트는 20개 안팎이다.
별도 명세 문서(md)를 두면 코드가 바뀔 때 문서를 같이 고쳐야 하고, 3주 프로젝트에서는 반드시 갈라진다.
FE는 명세를 보고 타입과 API 함수를 만든다. 정본이 하나여야 한다.

## 결정

- **서버 Swagger가 API 명세의 정본이다.** 별도 엔드포인트 명세 문서를 만들지 않는다
- 새 엔드포인트는 springdoc 어노테이션으로 코드에 문서화한다: `@Tag` · `@Operation` · `@ApiResponse`(스키마 · 예시) · `@Schema`(모든 DTO 필드) · `@Parameter`
- "Swagger에 요청 · 응답 · 오류가 보인다"가 BE API 일감의 완료 조건에 들어간다
- `docs/API.md`에는 모든 엔드포인트가 공유하는 공통 계약만 둔다 (스코프 · 응답 · 오류 형식 · 상태 전이)
- `docs/plans/3주_개발_계획.md` 7절의 최소 목록은 착수용이다. 구현되면 갱신하지 않는다

## 버린 대안

| 대안 | 왜 안 골랐나 |
|---|---|
| 도메인별 md 명세 + 명세에서 Mock 추출 | 명세 템플릿 하나에 API당 90줄. 3주에 쓸 비용이 아니다 |
| OpenAPI yaml을 손으로 쓰고 코드 생성 | 생성기 설정과 디버깅에 시간을 쓴다. 팀에 경험자가 없다 |

## 결과

- **좋아지는 것**: 코드와 명세가 갈라질 수 없다. FE는 `/v3/api-docs`로 타입을 뽑을 수 있다
- **감수하는 것**: 서버가 떠 있어야 명세를 본다. 어노테이션을 빠뜨리면 Swagger가 비어 보인다 — 리뷰에서 본다
- **다시 볼 시점**: FE · BE가 병렬로 착수해야 해서 코드 전에 계약이 필요할 때. 그 경우 해당 일감의 `[설명]`에 요청 · 응답 필드를 적는 것으로 대신한다 (JIRA-TEMPLATE 예시)
