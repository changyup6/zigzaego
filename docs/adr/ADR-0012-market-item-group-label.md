# ADR-0012: 식자재몰 상품은 품목군 기준표와 LLM 사전 분류 라벨로 찾고, 시세는 수집일마다 쌓아 플랫폼별 최저가 · 일별 추이를 낸다

- 상태: 채택
- 영역: backend · ai
- 결정 로그: [DECISIONS #71](../DECISIONS.md)
- 관련 이슈: S15P31A308-228 · S15P31A308-229 · S15P31A308-232
- 대체하는 것: [ADR-0010](ADR-0010-market-product-global-table.md) 의 "스냅샷 전체 교체" 와 "판정은 규칙 `ItemMatcher` 만" (표 자체 · 가게 스코프 예외 · JDBC 적재는 그대로)

## 맥락

- 재료별 최저가(`GET /ingredients/{id}/offers`)는 상품명 글자 매칭 + 규칙(`ItemMatcher`)으로 "정확한 품목" 을 골랐다. 처음 보는 검색어에서 약 90% 였고, 남은 오류는 표시 낱말이 없는 가공품(깐쇼새우 · 구운고등어 · 수비드 닭가슴살)과 규칙이 버리는 진짜 상품(흙대파 10단/망 · 1등급란)이라 목록을 늘려서는 끝나지 않았다. 네 방식 비교는 [검색 방식 비교 결과](../plans/2026-11-03_검색_방식_비교_결과.md).
- 발주 화면은 **플랫폼(사이트)별 최저가**와 **일별 시세 추이 그래프**를 보여 줘야 한다. 추이는 "같은 품목" 을 날마다 같은 기준으로 묶어야 그려지고, ADR-0010 의 전체 교체 적재로는 어제 값이 남지 않는다.
- 사이트마다 같은 품목을 다른 단위로 판다(계란 30구 · 1.8kg, 간장 1.8L · 1.9kg). 값을 나란히 놓으려면 품목마다 기준 단위와 환산값이 있어야 한다. 계란 ≠ 액란(난액 · 전란액), 두부 ≠ 순두부처럼 이름이 비슷해도 다른 품목인 것도 미리 정해야 한다.

## 결정

- **품목군 기준표** `market_item_group`(V8): 코드 · 이름 · 부모(부위 → 종) · 기준 단위(G · ML · EA) · 1개 무게 · 밀도 · 별칭. 정본은 `ai/seed/market_item_group.csv` 이고 DB 표는 그 복사본 — 바뀌면 `ai/scripts/market/make_item_group_sql.py` 출력으로 **새 마이그레이션**. 나누는 기준은 [품목군 분류 기준](../plans/2026-11-03_식자재몰_품목군_분류_기준.md) 3절(대체 가능 · 같은 가공 단계 · 같은 기준 단위).
- **상품명 라벨** `market_product_label`(V8): LLM 배치(백엔드 Spring Batch `marketProductLabelJob`, [ADR-0014](ADR-0014-market-label-spring-batch.md). 실험용은 `ai/scripts/market/classify_products.py`)가 고유 상품명마다 품목군 코드 · 형태(RAW · PREPARED · PROCESSED · NONFOOD · UNKNOWN) · 상품명에서 읽은 수량 · 확신을 매긴 것. 키 = 상품명. 검색할 때 LLM 을 부르지 않는다. 적재는 `import-market-products` 프로필에 `MARKET_LABELS_FILE` 로 upsert.
- **판정 순서**(`MarketCandidateFinder`): 재료 이름이 품목군 이름 · 별칭과 정확히 같으면(공백 무시, 겹치는 별칭 제외) **LABEL** — 라벨이 그 품목군의 원물 · 손질품(확신 0.6 이상)이라고 한 줄 + 라벨 없는 상품명 중 규칙이 맞다고 한 줄. 매핑이 없으면 **RULE** — 지금까지와 같은 이름 검색 + 규칙. 규칙 코드는 지우지 않는다.
- **단위 통일**: LABEL 경로의 단가는 품목군 기준 단위로 낸다. 총량은 크롤러 규격 해석 → 라벨 수량 순이고, 기준 단위가 개인 품목군에서 둘이 2배 넘게 어긋나면 라벨 개수를 쓴다. 환산값이 없는 단위(두부 2모)는 '다른 단위' 로 따로. 응답의 `toIngredientUnitFactor` 로 재료 기준 단위(원/g)로 바꿔 거래처 단가와 나란히 놓는다.
- **시세 이력**: `market_product` 는 수집일마다 쌓인다. 적재는 **파일에 든 수집일의 줄만 지우고 다시 넣는다**(한 트랜잭션). "지금 최저가" 는 사이트마다 가장 최근 수집일, 추이(`GET /ingredients/{id}/market-price-history`)는 (품목군, 사이트, 수집일)의 최저 단가. 인덱스 `(site, collected_on)` · `(product_name)`.
- 집계 규칙(이상치 = 같은 단위 중앙값의 5배 밖, 사이트 · 상품번호당 가장 싼 점포, 배달 가능 판매처 필터 ADR-0011)은 그대로이고 추이에서는 날짜마다 적용한다.

## 버린 대안

| 대안 | 왜 안 골랐나 |
|---|---|
| Elasticsearch + 한글 형태소(nori) | 형태소 분석은 계란찜을 계란+찜으로 쪼개 계란 검색에 더 잘 걸리게 한다(211 Kiwi 실험 · 228 비교 64%). 상품에 품목군을 매겨 주지 않아 추이 집계에 분류기가 따로 필요하고, 새 인프라(메모리 · 매주 색인)가 든다 |
| 벡터 검색 | '계란' 의 최근접이 계란찜 · 계란말이라 정밀도가 좋아질 이유가 없고 품목군 라벨을 만들어 주지 않는다. 일반 이름 고기(돼지고기 → 부위)는 품목군 표의 부모 관계로 푼다 |
| 앞말(prefix) 규칙 | 상품명이 브랜드 · ★ · 산지로 시작해 진짜 상품 대부분을 놓친다(재현율 12%) |
| 검색할 때마다 LLM 호출 | 요청마다 수백 ms 와 비용, 같은 상품명을 매번 다시 판정. 라벨은 상품명마다 한 번이면 된다 |
| 규칙 투표 자동 정답 + 분류기 학습(212 · 213) | 2026-11-02 폐기. 학습 · 정답 생성 단계 없이 LLM 라벨을 바로 쓰는 쪽이 단순하다 |
| 라벨 칸을 `market_product` 줄마다 붙임 | 같은 상품명이 사이트 · 점포 · 수집일마다 반복된다. 상품명 표 하나를 조인하면 다시 분류할 때 한 번에 바뀐다 |
| 재료에 품목군을 직접 저장하는 칸 | 이름 매핑이 틀리는 재료가 보이면 그때 사장님이 고르는 칸을 더한다 |

## 결과

- **좋아지는 것**: 발주 화면이 플랫폼별 최저가와 일별 추이를 같은 기준(품목군 × 기준 단위)으로 보여 준다. 규칙이 못 거르던 가공품과 규칙이 버리던 진짜 상품을 라벨이 바로잡는다. 계란 1.8kg 과 30구, 간장 1.9kg 과 1.8L 를 한 표에 놓는다.
- **감수하는 것**: 품목군 표(182개, 부모 4개 포함) 밖 재료는 지금처럼 RULE 이다. 라벨이 없는 새 상품명은 다음 배치까지 규칙으로 판정한다. LLM 라벨도 틀린다 — 표본 200개 95% 기준(229)을 못 넘기면 프롬프트 · 표를 고치고 `label_version` 을 올려 다시 돌린다. 시세가 날마다 쌓이면 표가 커진다(48만 줄 × 일수).
- **다시 볼 시점**: 조회가 1초를 넘으면 `(item_group_code)` 조인 결과를 일별 집계 표로 미리 만든다. 수집일이 90일을 넘으면 오래된 줄을 지우는 보관 기간을 정한다. 품목군이 300개를 넘으면 배치 프롬프트를 카테고리별로 나눈다.
