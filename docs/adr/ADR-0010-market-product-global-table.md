# ADR-0010: 식자재몰 시세는 가게 스코프 없는 전역 표 `market_product` 에 스냅샷 전체 교체로 적재한다

- 상태: 일부 대체됨 → [ADR-0012](ADR-0012-market-item-group-label.md) (전체 교체 적재 → 수집일 단위 적재, 규칙 판정 → 품목군 라벨 우선). 전역 표 · 가게 스코프 예외 · JDBC 적재는 유효
- 영역: backend
- 결정 로그: [DECISIONS #69](../DECISIONS.md)
- 관련 이슈: S15P31A308-232 · S15P31A308-231

## 맥락

- 가격 비교(DECISIONS #37 · #48)는 재료마다 식자재몰 최저가를 보여 준다. 그 원천은 크롤러(`foodspring-crawler`)가 매주 만드는 통합 데이터셋(7개 몰, 약 48만 줄 Parquet)이고, 지금은 크롤러 저장소의 DuckDB 스크립트로만 조회할 수 있다. 서비스 DB 에는 이 데이터가 없다.
- 시세는 어느 가게의 것도 아니다. 모든 가게가 같은 상품 · 같은 가격을 본다. 그런데 ADR-0002 는 모든 표에 `store_id` 를 두고 모든 조회에 가게 조건을 걸라고 한다. 48만 줄을 가게 수만큼 복제하는 것은 뜻이 없다.
- 데이터셋은 수집마다 전체가 새로 만들어진다(지난주 가격은 크롤러 `price_change.py` 가 따로 비교). 서비스가 필요한 것은 "지금 최저가" 뿐이라 이력을 쌓을 이유가 없다.
- 상품명으로 재료를 찾는 판정(계란 ≠ 계란찜)은 크롤러 `match.py` 에 규칙으로 있고 정확도 약 90% 로 측정됐다(S15P31A308-210). 서비스에서도 같은 답이 나와야 한다.

## 결정

- Flyway `V5__market_product.sql` 에 **가게 스코프 없는** 전역 참조 표 `market_product` 를 둔다. 데이터셋 열(사이트 · 점포지역 · 상품번호 · 상품명 · 규격 · 판매가 · 총량 · 단위 · 단위가격 · URL · 수집일 · 묶음번호)을 그대로 담는다. ADR-0002 의 유일한 예외이며, **가게 스코프는 이 표를 읽는 쪽이 건다**: 재료 id 는 로그인한 가게로 좁혀 읽고(404), 시세는 그 재료 이름으로만 찾는다. 이 표를 직접 노출하는 API 는 두지 않는다.
- JPA 엔티티를 두지 않는다. 적재(`MarketProductJdbcRepository.insertAll`) · 후보 조회(`findCandidates`)만 JDBC 로 한다. `StoreScopeGuardTest` 는 `storeId` 가 있는 엔티티만 검사하므로 이 표는 걸리지 않는다.
- 적재는 운영자가 돌리는 `import-market-products` 프로필(`MarketProductImportRunner`)이 크롤러가 내보낸 CSV(`scripts/export_market_csv.py`) 한 파일을 **한 트랜잭션에서 표 전체를 비우고 다시 넣는다**. 실패하면 이전 스냅샷이 남는다. 수집(S15P31A308-123) 과 적재는 분리한다 — 서비스는 사이트에 요청을 보내지 않는다.
- 품목 판정은 크롤러 `match.py` 를 그대로 옮긴 `ItemMatcher` 가 한다. 후보는 DB 정규식(`~*`)으로 거르고 정확 판정은 Java 에서 한다. 규칙을 바꾸면 **Python 과 Java 를 같이 고치고** `ItemMatcherTest` 기대값을 Python 으로 다시 만든다.
- 규격 해석(총량 · 단위가격)은 크롤러가 계산한 값을 그대로 쓴다. 서비스에서 다시 계산하지 않는다.

## 버린 대안

| 대안 | 왜 안 골랐나 |
|---|---|
| 가게마다 `store_id` 를 붙여 복제 | 48만 줄 × 가게 수. 같은 값을 여러 번 저장할 뿐 격리할 것이 없다 |
| 서비스가 크롤러 DuckDB · Parquet 를 직접 읽음 | 서비스에 Python · 파일 의존이 생기고 스테이징에 데이터 파일을 둬야 한다. PostgreSQL 한 곳이 단순하다 |
| 날짜별 스냅샷을 쌓는 이력 표 | 서비스는 "지금 최저가" 만 쓴다. 주간 변화 분석은 크롤러 쪽(S15P31A308-192)이 한다. 48만 줄 × 주가 쌓이면 조회가 느려진다 |
| 식봄 · 쿠팡 단가를 핵심 재료마다 하루 1회 저장(설계 5.5절 원안) | 재료 ↔ 상품 매칭을 미리 정해야 하고 쿠팡은 수집할 수 없다(S15P31A308-122). 전체 데이터셋을 두면 어떤 재료든 이름으로 찾는다 |
| 재료 ↔ 몰 상품 매핑 표를 사장님이 직접 관리 | 사장님 일이 늘고, 데이터셋이 주마다 바뀌어 상품번호가 사라진다 |

## 결과

- **좋아지는 것**: 서비스가 어떤 재료든 이름만으로 7개 몰 최저가를 1초 안에 답한다. 적재가 한 번의 명령이고 실패해도 이전 값이 남는다. 판정 규칙이 크롤러와 같아 정확도 측정(약 90%)을 그대로 믿을 수 있다.
- **감수하는 것**: 상품명 부분 일치라 인덱스를 못 타고 48만 줄을 순차로 읽는다(수백 ms). 가게 스코프 예외가 하나 생겨 `StoreScopeGuardTest` 가 이 표를 보지 않는다. 판정 규칙을 두 언어에 두 번 적는다. 배달 가능 판매처 필터는 ADR-0011(S15P31A308-230)이 읽는 쪽에 붙였다.
- **다시 볼 시점**: 조회가 1초를 넘으면 `pg_trgm` GIN 인덱스. 데이터셋이 매주 2개 이상 쌓이거나 가격 추이가 필요해지면 이력 표. 판정 규칙이 세 번째 언어로 가거나 LLM 사전 분류(S15P31A308-229)가 들어오면 분류 결과를 표의 열로 적재하고 규칙 코드를 지운다.
